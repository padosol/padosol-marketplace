# 사례 선정 · 안티패턴 · 검산

---

## 1. 사례 선정 규칙

**사례 하나당 서로 다른 역량 하나를 증명해야 한다.**

권장 역량 축(서로 겹치지 않는 배치의 예):

| 축 | 증명하는 것 |
|---|---|
| 정합성 자동화 / CI | 사람 검토에 의존하던 결함을 기계로 옮긴 능력 |
| 동시성 · 리소스 격리 | 자원 경합을 이해하고 경계를 그은 능력 |
| 쿼리 최적화 · 실행 계획 | 계측 기반으로 병목을 특정한 능력 |
| 환경 차이 · 테스트 전략 | 운영과 테스트의 간극을 좁힌 능력 |

- 새 사례가 **기존 축과 겹치면 추가하지 말고 기존 사례를 보강**한다.
- 사례는 **4~5개가 상한**. 그 이상은 읽히지 않는다.
- 축이 겹치는데도 사용자가 추가를 원하면, 겹친다는 사실을 알리고
  "기존 사례 보강" 대안을 먼저 제시한다.

---

## 2. 안티패턴

| 쓰지 말 것 | 왜 |
|---|---|
| "성능을 개선했습니다" | 증상·원인이 없으면 검증 불가능한 주장 |
| 원인 없이 문제 → 해결로 점프 | 운이 좋았던 건지 알아낸 건지 구분이 안 됨 |
| 도구 나열 ("Testcontainers를 도입했습니다") | "H2가 collation을 해석하지 않아서" 같은 **필연**이 있어야 함 |
| 대가 없는 100% 성공담 | 트레이드오프를 모르는 사람으로 보임 |
| 팀 성과와 내 몫이 안 나뉜 서술 | "누가 했나요"에서 무너짐 |
| 측정 환경 없는 개선율 | 90%가 어떤 조건의 90%인지 없으면 숫자가 아님 |

## 3. 최종 체크리스트

사례를 쓴 뒤 이 **순서대로** 검산한다. 통과 못 한 항목은 고치거나, 못 고치면 `✍️` 로 남기고
사용자에게 무엇이 비었는지 보고한다.

- [ ] 1. 제목만 읽고도 무슨 일이 있었는지, 얼마나 좋아졌는지 알 수 있는가
- [ ] 2. 문제 블록에 **발견 시점**이 있는가
- [ ] 3. 문제 블록에 **개별 수정으로 안 되는 이유**가 있는가
- [ ] 4. 원인 블록에 **확인 수단**(도구·로그·실행 계획)이 있는가
- [ ] 5. 원인 블록에 **기존 안전망이 못 잡은 이유**가 있는가
- [ ] 6. 해결의 모든 숫자가 문제·원인에서 **근거**를 갖는가
- [ ] 7. 해결에 **실패 경로 처리**가 있는가
- [ ] 8. 측정에 **수치 / 구조적 효과 / 운영성**이 다 있는가
- [ ] 9. **측정 환경**(건수·동시성·데이터 규모·인스턴스 스펙)이 적혀 있는가
- [ ] 10. 비고에 **버린 대안 · 대가 · 한계**가 다 있는가
- [ ] 11. 상단 요약(Introduce)의 수치와 본문 수치가 **정확히 일치**하는가
- [ ] 12. 이 사례가 다른 사례와 **다른 역량**을 증명하는가
- [ ] 13. `✍️` 마커가 남아 있지 않은가

### 자주 걸리는 항목

- **3번** — 가장 자주 빠진다. 없으면 해결의 재발 방지 구조가 과잉 대응으로 읽힌다.
- **9번** — 수치를 쓴 사례는 대부분 여기서 걸린다. 모르면 지어내지 말고 물어본다.
- **13번** — 마커가 남았는데 "완성했습니다"라고 보고하지 않는다. 남은 마커를 그대로 나열한다.
