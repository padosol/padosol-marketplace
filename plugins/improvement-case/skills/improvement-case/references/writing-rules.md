# 블록별 작성 규칙

SKILL.md 의 5블록 최소 요건을 실제 문장으로 만드는 방법. 예시는 모두 실제 사례에서 뽑은 것이다.

---

## 제목

```
N. [증상 — 과거형 서술 한 문장] — [조치], [결과 수치]
```

**좋은 예**

- `1. 조건절이 조용히 빠져 잘못된 데이터가 나갔다 — 매퍼 102개·조건식 854건 전수 검증을 CI로, 4건 사전 발견`
- `2. 업로드가 몰리면 일반 API 응답까지 밀렸다 — 전용 스레드 풀로 격리, 동시 실행 2건 제한`
- `3. 목록 조회가 3초씩 걸렸다 — 실행 계획을 보니 N×M 풀스캔, 3초 → 0.3초`

**흔들리기 쉬운 지점**

- 조치 자리에 **원인**을 넣는 변형은 원인 자체가 임팩트 있을 때만 허용한다(예 3번).
  기본형은 조치 자리에 조치를 쓴다.
- 결과 수치가 없다면 **차단한 것**을 쓴다.
  → `운영에서만 터지던 조인 실패를 CI에서 차단`
- 증상을 기술 용어로 시작하지 않는다.
  ✗ `MyBatis OGNL 파싱 이슈` → ✓ `조건절이 조용히 빠져 잘못된 데이터가 나갔다`

---

## 문제 — 증상 + 발견 시점 + 왜 못 막았나

세 가지를 반드시 담는다.

**1) 관측된 증상**
응답 시간, 예외, 실패한 동작. 영향 범위(어떤 API·누가)를 같이 쓴다.

**2) 언제 드러났나**
"배포 후 그 쿼리가 호출되는 순간에", "운영에서만" —
**발견이 늦었다는 사실 자체가 문제의 크기**다. 늦게 발견됐다면 그걸 숨기지 말고 쓴다.

**3) 개별 수정으로 끝나지 않는 이유**

> 사람이 확인하지 않으면 걸러지지 않는 결함이라 개별 수정만으로는 반복을 막을 수 없었다.

이 한 줄이 있어야 해결 블록의 CI 도입이 **과잉 대응으로 안 보인다.** 사례에서 가장 자주 빠지는 문장이다.

**4) 제약 조건은 여기서 깐다**
"4코어 인스턴스라", "운영 DB 스키마를 바꿀 수 없어서" —
해결 블록에서 갑자기 튀어나오는 숫자는 방어가 안 된다. 근거가 될 제약은 문제 블록에 먼저 심는다.

---

## 원인 — 확인 수단 + 메커니즘 + 기존 안전망의 구멍

| 항목 | 왜 필요한가 | 예 |
|---|---|---|
| 확인 수단 | 추측이 아니라 **계측**이었음을 증명 | `EXPLAIN ANALYZE`, Testcontainers, 스레드 덤프, APM 트레이스 |
| 메커니즘 한 줄 | 원리를 아는지 보는 자리 | "OGNL의 단일 문자 파싱으로 조건절이 조용히 빠짐" |
| 기존 안전망이 못 잡은 이유 | 해결이 왜 **그 지점**을 건드리는지 설명 | "매퍼 XML은 컴파일 대상이 아니다", "H2는 collation을 해석하지 않는다", "DDL은 정상 성공한다" |

세 번째가 이 형식의 심장이다. 컴파일·테스트·배포 중 **어느 그물의 코가 이 결함을 통과시켰는지**를
한 줄로 특정한다. 이게 없으면 해결이 임의의 도구 도입처럼 읽힌다.

---

## 해결 — 조치 + 근거를 한 문장에

**조치만 나열하지 않는다.** 근거를 같은 문장에 붙인다.

- ✗ `동시 실행 2건으로 제한`
- ✓ `CPU 코어 수와 DB 커넥션 상한을 고려해 동시 실행 2건 제한`

**개별 수정과 재발 방지를 나란히 쓴다.**

> `.equals()` 로 전환하고 **+** 전체를 점검해 컨벤션으로 정리

**실패 경로를 쓴다.**
`AbortPolicy` 즉시 거부, 중간 산출물·부분 반영분 정리, 재시도 상한 —
성공 경로만 있는 설계는 운영 경험이 없어 보인다.

**부수 조치도 한 줄 넣는다.**
`TaskDecorator` 로 traceId 전파 같은 것. 비동기로 바꾸면 추적이 끊긴다는 걸
**알고 있었다는 신호**다.

항목은 **3~4개**. 그 이상은 중요도가 흐려진다.

## 측정 — 3층으로 쌓는다

| 층 | 내용 | 예 |
|---|---|---|
| 1층 수치 | before → after, 개선율, 차단 건수 | `3초 → 0.3초 (90% 개선)`, `4건 사전 발견, 잔여 0건` |
| 2층 구조적 효과 | 앞으로 **자동으로** 걸러지는 것 | "신규 매퍼 추가 시 별도 조치 없이 동일 검사 적용" |
| 3층 운영성 | 안정화·추적 가능성 | 커넥션 풀 안정화, 요청 단위 로그 추적 가능 |

**측정 환경을 빼면 1층은 무효다.**
데이터 건수 · 동시 사용자 수 · 파일 크기와 건수 · 인스턴스 스펙 —
없으면 "그 3초는 어떤 조건이었죠?" 한 방에 무너진다. 모르면 `✍️` 로 남기고 반드시 확인한다.

---

## 비고 — 면접 방어용 3종 세트

| 질문 유형 | 준비할 것 |
|---|---|
| 버린 대안 | "왜 MyBatis를 걷어내고 JPA로 통일하지 않았나" — 두 개를 같이 쓰면 반드시 나오는 질문 |
| 치른 대가 | CI 시간 증가분, 인덱스 추가로 느려진 쓰기 |
| 남은 한계 | "이 검사로도 못 잡는 결함은 무엇인가" |

**한계를 먼저 말하는 사람이 더 믿음직하다.** 분량은 짧아도 되지만 비어 있으면 안 된다.

# 문체 규칙

## 위치별 문체

| 위치 | 문체 | 예 |
|---|---|---|
| 제목 · 문제 · 원인 | 과거형 서술 | "~드러났다", "~밀렸다", "~물고 있었다" |
| 해결 · 측정 | 명사형 압축 | "~차단", "~확보", "~감소" |

앞은 이야기, 뒤는 이력서. 이 전환이 "순수 개조식은 딱딱하다"는 문제를 푸는 방식이다.

## 볼드

- 문장 전체를 볼드 처리하지 않는다.
- **판단이 걸린 지점**에만 — 수치, 핵심 기술 용어, 인과의 연결점.
- 한 항목에 볼드가 **3군데를 넘으면** 강조가 사라진다.

## 숫자

- **반올림하지 않는다.** 102개, 854건, 4건 — 원단위 그대로 쓸 때 실제로 세어봤다는 신뢰가 생긴다.
- 같은 수치는 상단 요약(Introduce)과 본문에서 **글자까지 동일**하게 유지한다.
  요약과 본문의 숫자가 어긋나는 순간 전체가 의심받는다.

## 의도를 드러내는 동사

"~하도록 유도", "~하도록 설계", "~하도록 구성".
결과만 쓰지 말고 **의도한 결과였음**을 드러낸다.
