# 문제 / 개선 사례 작성

## 이 스킬이 지키려는 것

좋은 사례가 증명하는 건 **"고쳤다"가 아니라 "어떻게 알아냈고, 왜 다시 안 생기게 만들었나"** 다.

```
증상이 운영에서만 드러났다
  → 계측/근거로 원인을 특정했다
    → 개별 수정 + 재발을 막는 구조를 함께 넣었다
      → 수치와 구조적 효과를 둘 다 남겼다
```

이 골격에서 벗어나는 글은 **작업 기록**이지 개선 사례가 아니다.
골격의 칸이 비면 문장을 예쁘게 다듬지 말고 **빈 칸을 사용자에게 질문**한다.

## 절대 규칙 — 추측 금지

수치·환경·도구 이름을 **지어내지 않는다.** 사용자가 말하지 않은 값은 `✍️` 마커로 남기고 질문한다.

```
- 3초 → 0.3초 (✍️ 측정 조건: 데이터 건수 / 동시 사용자 수 확인 필요)
```

`✍️` 가 하나라도 남아 있으면 그 사례는 **미완성**이다. 사용자에게 남은 마커를 명시적으로 알린다.

## 작업 절차

1. **재료 수집.** 사용자 설명 + (있다면) 코드·커밋·이슈에서 5블록 재료를 뽑는다.
   비는 칸은 아래 "5블록 최소 요건"을 기준으로 **한 번에 모아서** 질문한다.
2. **역량 축 확인.** 기존 사례 목록이 있으면 축이 겹치는지 본다. 겹치면 새로 추가하지 말고
   **기존 사례를 보강**한다. 판단 기준은 `references/quality-gate.md` 의 "사례 선정 규칙".
3. **제목 확정.** 아래 제목 공식으로 한 줄을 먼저 만든다. 제목이 안 써지면 재료가 부족한 것이다.
4. **본문 작성.** `assets/case-template.md` 를 복사해 5블록을 채운다.
   블록별 상세 규칙·문체는 `references/writing-rules.md` 를 따른다.
5. **검산.** `references/quality-gate.md` 의 13항목 체크리스트를 순서대로 통과시킨다.
   통과 못 한 항목은 고치거나, 못 고치면 `✍️` 로 남기고 사용자에게 보고한다.
6. **수치 동기화.** 문서 상단 요약(Introduce)이 있으면 본문 수치와 **글자까지 동일**한지 확인한다.

## 제목 공식

```
N. [증상 — 과거형 서술 한 문장] — [조치], [결과 수치]
```

| 요소 | 규칙 | 예 |
|---|---|---|
| 증상 | 기술 용어가 아니라 **현상**으로 시작. 누가 아팠는지가 보여야 한다 | "업로드가 몰리면 일반 API 응답까지 밀렸다" |
| 조치 | 수단 + 범위. 숫자를 여기서 한 번 쓴다 | "매퍼 102개·조건식 854건 전수 검증을 CI로" |
| 결과 | before → after, 또는 차단 건수 | "3초 → 0.3초" |

- 원인이 그 자체로 임팩트 있을 때만 조치 자리에 원인을 넣을 수 있다
  (예: "실행 계획을 보니 N×M 풀스캔"). **기본은 조치 자리**다.
- 결과 수치가 없는 사례는 대신 **"무엇을 막았는지"** 를 넣는다
  (예: "운영에서만 터지던 조인 실패를 CI에서 차단").

## 5블록 최소 요건

| 블록 | 반드시 들어가는 것 | 빠지면 생기는 일 |
|---|---|---|
| **문제** | ① 관측된 증상 ② 언제 드러났나 ③ 개별 수정으로 안 되는 이유 ④ 제약 조건 | 3번이 없으면 CI 도입 등이 과잉 대응으로 보인다 |
| **원인** | ① 확인 수단(계측) ② 메커니즘 한 줄 ③ 기존 안전망이 못 잡은 이유 | 1번이 없으면 운으로 찾은 건지 알아낸 건지 구분이 안 된다 |
| **해결** | ① 조치 + 근거를 한 문장에 ② 개별 수정 + 재발 방지 구조 ③ 실패 경로 ④ 부수 조치 | 3번이 없으면 운영 경험이 없어 보인다 |
| **측정** | ① 수치 ② 구조적 효과 ③ 운영성 ④ **측정 환경** | 4번이 없으면 "그 3초는 어떤 조건이죠?" 한 방에 무너진다 |
| **비고** | ① 버린 대안 ② 치른 대가 ③ 남은 한계 | 비면 트레이드오프를 모르는 사람으로 보인다 |

**해결에 등장하는 모든 숫자는 문제·원인에서 근거를 갖는다.**
(예: "동시 실행 2건 제한"을 쓰려면 문제 블록에 "4코어 인스턴스라"가 먼저 나와야 한다.)

## 문체 한 줄 요약

| 위치 | 문체 |
|---|---|
| 제목 · 문제 · 원인 | 과거형 서술 — "~드러났다", "~밀렸다" |
| 해결 · 측정 | 명사형 압축 — "~차단", "~확보", "~감소" |

앞은 이야기, 뒤는 이력서. 볼드는 판단이 걸린 지점에만(한 항목에 3군데 이하).
숫자는 반올림하지 않는다 — 102개, 854건, 4건. 상세는 `references/writing-rules.md`.

## 언제 쓰고, 언제 안 쓰는가

- **쓴다:** 개선 사례를 새로 쓸 때, 기존 사례를 보강·검산할 때, 방금 해결한 이슈를 경력
  자산으로 남길 때, "이 경험 이력서에 어떻게 쓰지"를 물을 때.
- **안 쓴다:** 자기소개서·지원 동기, 이력서 전체 구조 첨삭, PR/커밋 설명 작성.
  이 스킬은 **개선 사례 한 건의 구조**가 본분이다.
