# portfolio-case

포트폴리오 문제해결 사례를 **6블록(문제 · 원인 · 측정 · 해결 · 평가 · 비고)** 구조로 작성하는 Claude Code plugin.

지키려는 것은 하나다:

> **소제목만 세로로 훑어도 사례 전체가 추적된다**

```
문제 1  간헐적 데드락        →  원인 1  비관적 락 사용
문제 2  매월 데드락          →  원인 2  다중 쿼리 결과
문제 3  수정 이후에도 발생    →  원인 3  쿼리 결과가 없는 경우
```

같은 번호는 같은 대상을 가리킨다. 대응이 어긋나는 자리가 곧 논리 구멍이다.
그래서 이 플러그인은 본문을 바로 쓰지 않고 **대응표를 먼저 세워 구멍을 잡은 뒤** 본문을 쓴다.

## 설치

marketplace 등록 후:
```
/plugin install portfolio-case@padosol
```

## 사용

```
이 항목들 포트폴리오로 정리해줘
```

```
데드락 고친 거, 문제해결 사례로 써줘
```

```
포트폴리오 사례 2번 좀 봐줘 — 뭐가 비었는지
```

**쓴다:** 포트폴리오 사례를 새로 쓸 때, 기존 사례를 6블록으로 재구성할 때,
러프한 항목 나열을 읽히는 문서로 만들 때, 사례의 논리 구멍을 찾을 때.

**안 쓴다:** 자기소개서 · 지원 동기, 이력서 전체 첨삭, PR/커밋 설명 작성.

## 블록 구성

| 순서 | 블록 | 담는 것 |
|---|---|---|
| 1 | 문제 | 관측된 증상 |
| 2 | 원인 | 그 증상을 만든 구조 |
| 3 | **측정** | **해결 전** — 문제를 어떻게 재현·계측했나 |
| 4 | 해결 | 실제로 적용한 조치 |
| 5 | **평가** | **해결 후** — 어떤 환경에서 무엇을 확인했나 |
| 6 | 비고 | 검토했다가 **채택하지 않은 대안** |

**측정과 평가는 해결을 사이에 두고 나뉜다.** 측정은 고치기 전에 문제를 손에 잡히게 만든 단계
(재현 테스트, 계측)이고, 평가는 고친 뒤 통했는지 확인한 단계다. 한 블록에 섞으면
"재현할 줄 안다"와 "검증했다" 중 하나가 사라진다.

## 무엇을 강제하는가

### 1. 마크다운 포맷 고정

| 위치 | 마커 | 소제목 | 하위 들여쓰기 |
|---|---|---|---|
| 문제 · 원인 · 해결 | `1.` `2.` `3.` | `**볼드**` | 스페이스 4칸 |
| 측정 · 평가 | 없음 | `**볼드**` 단독 줄 | 없음 (0칸) |
| 비고 | `-` | `**볼드**` | 스페이스 4칸 |

탭을 쓰지 않고, 모든 문장은 존댓말로 끝내며, 본문 문장에는 볼드를 쓰지 않는다(소제목만 볼드).

### 2. 비고는 버린 대안만

```markdown
### 비고

- **배치 서버 고려**
    - 배치 서버로 데이터를 삽입하는 방법을 고려하였으나, 삽입에 오랜 시간이 걸리고 해당 API의 트래픽이 많아 병목이 우려되어 다른 방안을 채택하였습니다.
- **MySQL 분산 락 고려**
    - MySQL의 USER-LEVEL LOCK은 커넥션 연결 부족 우려로 인해 피하고, Redis를 도입하여 분산 락을 사용하였습니다.
```

- 항목 **2~3개**, 각 **1~2줄**.
- 한 항목 = **대안 + 버린 이유 + 대신 택한 것**.
- **한계 · 치른 대가 · 미확인 구간 · 다음 과제 · 확장 적용은 넣지 않는다.**
  비고가 길어지면 사례 전체가 변명처럼 읽힌다.

**버린 대안은 해결이 아니라 비고에 쓴다.** 해결 블록에는 실제로 적용한 조치만 남는다.

### 3. 블록별 주어와 시제

| 블록 | 주어 | 시제 | 대표형 |
|---|---|---|---|
| 문제 | 사용자 / 시스템 | 현재형 | "~가 발생합니다" |
| 원인 | 코드 / 설정 / 쿼리 | 현재형 진행 | "~를 사용하고 있습니다" |
| 측정 | 나 / 테스트 | 현재형 | "~하여 재현합니다" |
| 해결 | 나 | 과거형 | "~하였습니다" |
| 평가 | 나 / 검증 | 현재형 | "~정상 작동 여부를 확인합니다" |
| 비고 | 나 | 과거형 | "~고려하였으나 ~채택하였습니다" |

### 4. 원인은 구조를 지목하되, 추측과 조건부를 구분

| 구분 | 예 | 판정 |
|---|---|---|
| 규명 불확실 | "락 경합으로 추정됩니다" | ✗ |
| 조건부 발생 | "빈 row에 락을 걸면 갭 락이 생겨 데드락이 발생할 가능성이 높습니다" | ✓ |

앞은 "아직 모른다", 뒤는 "구조는 알고 있고 확률적으로 터진다"는 뜻이다.

### 5. 지어내지 않는다

도구 이름 · 측정 조건 · 수치를 추측으로 채우지 않는다.
사용자가 말하지 않은 값은 `✍️` 마커로 남기고 되묻는다.
마커가 하나라도 남아 있으면 미완성이며, 완성했다고 보고하지 않는다.

## 검산 6문항

1. 6블록이 `문제 → 원인 → 측정 → 해결 → 평가 → 비고` 순서로 있고, 소제목만 읽어도 흐름이 잡히는가
2. **문제 N번과 원인 N번이 같은 대상을 가리키고, 각 문제가 어느 해결로 이어지는지 추적되는가**
3. 문제 블록에 원인이 섞여 있지 않은가
4. 측정은 해결 전 재현, 평가는 해결 후 검증으로 나뉘어 있는가
5. **비고에 버린 대안만 있고, 항목 2~3개에 각 1~2줄인가**
6. 측정과 평가에 도구와 조건이 있는가

## improvement-case 와의 차이

두 플러그인 모두 문제해결 사례를 다루지만 **최적화 대상이 다르다.**

| | `portfolio-case` | `improvement-case` |
|---|---|---|
| 산출물 | 포트폴리오 문서 | 이력서 · 경력기술서 사례 한 건 |
| 블록 | 6블록 (측정·평가 분리) | 5블록 (문제·원인·해결·측정·비고) |
| 구조 장치 | 소제목 + 블록 간 번호 대응표 | 제목 공식(증상 — 조치, 수치) |
| 버린 대안 | 비고 | 해결 |
| 비고 범위 | 버린 대안만 | 대안 · 대가 · 한계 |
| 검산 | 6문항 | 13항목 |

**읽히는 문서**를 만들 때는 이 플러그인, **한 줄로 압축**할 때는 `improvement-case` 를 쓴다.
