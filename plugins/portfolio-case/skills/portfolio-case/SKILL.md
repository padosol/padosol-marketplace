# 포트폴리오 5블록 작성

## 이 스킬이 지키려는 것

좋은 사례는 **소제목만 세로로 훑어도 전체가 추적된다.**

```
문제 1  간헐적 로그인 끊김        문제 2  응답 지연 및 요청 실패
원인 1  인스턴스 로컬 세션 저장    원인 2  리다이렉트당 단건 조회
해결 1  세션 저장소 외부화        해결 2  로컬 캐시 적용
측정 1  세션 유실 문의 건수       측정 2  평균 응답 시간, 조회 호출 수
```

같은 번호는 **같은 대상**을 가리킨다. 대응이 맞아떨어지면 읽는 사람이 사례를 끝까지 따라오고,
어긋나면 **그 자리가 곧 논리 구멍**이다.

그래서 이 스킬은 본문을 바로 쓰지 않는다. **대응표를 먼저 세우고, 거기서 구멍을 잡은 뒤** 본문을 쓴다.

## 절대 규칙 — 지어내지 않는다

수치 · 측정 도구 · 측정 조건 · 확인 수단을 **추측으로 채우지 않는다.**
사용자가 말하지 않은 값은 `✍️` 마커로 남기고 질문한다.

```
- 평균 응답 시간 820ms → 95ms (✍️ 측정 도구와 조건 확인 필요)
```

`✍️` 가 하나라도 남아 있으면 그 사례는 **미완성**이다. 완성했다고 보고하지 말고 남은 마커를 그대로 나열한다.

이 규칙이 특히 중요한 이유는 **원인 블록이 단정형을 강제**하기 때문이다.
확인되지 않은 것을 단정하면 그건 문체 규칙을 지킨 게 아니라 거짓말이다.
확인 못 한 영역은 원인에서 흐리지 말고 **비고의 "미확인 구간"으로 분리**한다.

## 작업 절차

1. **재료 분해.** 사용자가 준 항목 · 메모 · 로그를 문장 단위로 쪼개 5블록 중 어디에 속하는지 배정한다.
   이 단계에서 **원인이 섞인 문제 문장**과 **문제 블록에 들어간 수치**를 먼저 걷어낸다.

2. **대응표 확정.** 소제목만으로 아래 표를 만들어 **사용자에게 먼저 보여준다.**

   | | 1번 | 2번 |
   |---|---|---|
   | 문제 | 간헐적 로그인 끊김 | 응답 지연 및 요청 실패 |
   | 원인 | 인스턴스 로컬 세션 저장 | 리다이렉트당 단건 조회 |
   | 해결 | 세션 저장소 외부화 | 로컬 캐시 적용 |
   | 측정 | 세션 유실 문의 건수 | 평균 응답 시간, 조회 호출 수 |

   빈 칸이 생기면 그게 질문 목록이다. **빈 칸을 문장으로 덮지 말고 한 번에 모아서 묻는다.**
   특히 측정 칸이 비면 "무엇을 어떤 도구로 어떤 조건에서 쟀는지"를 묻는다.

3. **본문 작성.** `assets/portfolio-template.md` 를 복사해 채운다.
   블록별 상세 규칙과 표현 사전은 `references/block-rules.md` 를 따른다.

4. **검산.** `references/quality-gate.md` 의 6문항을 순서대로 통과시킨다.
   못 고친 항목은 `✍️` 로 남기고 사용자에게 보고한다.

5. **배경 정리.** 길이가 넘치면 대개 배경 설명이 문제 · 원인 블록에 스며든 것이다.
   배경은 사례 제목 아래 **"상황" 한 줄**로 빼고 5블록은 건드리지 않는다.

## 소제목 규칙

블록은 **소제목 + 내용**으로 쓴다. 한 블록에 소제목이 여럿, 소제목 하나에 내용이 여러 줄 올 수 있다.

| 규칙 | 내용 |
|---|---|
| 명사구로 끝낸다 | ✗ "로그인이 끊김" → ✓ "간헐적 로그인 끊김" |
| 4~12자로 압축한다 | 목차만 훑어도 무슨 사례인지 보이는 길이 |
| 블록별로 관점을 바꾼다 | 문제는 **증상**, 원인은 **구조**, 해결은 **조치**를 이름에 담는다 |
| 내용은 1~3줄 | 넘으면 소제목을 쪼갤 신호 |

블록마다 관점이 바뀌어야 대응표가 정보를 준다.
문제도 "세션 유실", 원인도 "세션 유실"이면 한 칸이 낭비된다.

## 블록별 주어와 시제

주어가 섞이면 "성능이 개선되도록 캐시를 적용해서 응답이 빨라졌습니다" 같은 뭉개진 문장이 나온다.

| 블록 | 주어 | 시제 | 대표형 |
|---|---|---|---|
| 문제 | 사용자 / 시스템 | 현재형 | "~하는 현상 발생" |
| 원인 | 코드 / 설정 / 쿼리 | 과거형 단정 | "~였습니다" |
| 해결 | 나 | 과거형 능동 | "~를 적용했습니다" |
| 측정 | 지표 | 수치 대비 | "~ → ~" |
| 비고 | 나 / 남은 과제 | 미래·조건형 | "~는 필요합니다" |

## 수치는 원인과 측정에만 둔다

문제 블록에 "3초 걸림"을 쓰면 **측정 블록이 할 말을 잃는다.**

- 문제: 조회가 느리다는 문의가 접수됨
- 측정: 평균 응답 3초 → 0.3초

## 블록별 핵심 한 줄

| 블록 | 반드시 지키는 것 | 어기면 |
|---|---|---|
| **문제** | 관측된 증상만. 원인 암시 금지 | "때문에 / 탓에 / 미흡하여"가 있으면 원인 블록으로 옮긴다 |
| **원인** | 확인한 사실 → 확정된 원인, 단정형 | 추측성 표현이 남으면 규명이 덜 된 채 조치한 인상 |
| **해결** | 동사로 시작 + **선택하지 않은 대안 한 줄** | 기술 나열은 누구나 한다. 선택 이유는 겪은 사람만 쓴다 |
| **측정** | 무엇을 / 어떤 도구로 / 어떤 조건에서 | 도구와 조건 없는 수치는 한 방에 무너진다 |
| **비고** | 한계와 트레이드오프 | 비면 "운 좋게 됐다"로 읽힌다 |

상세와 표현 사전은 `references/block-rules.md`.

## 문체 한 줄 요약

**소제목은 명사형, 첫 내용은 개조식, 부연은 서술형 한 문장.**

```
1. 리다이렉트당 단건 조회
   - 리다이렉트 처리마다 UUID 단건 조회가 발생.
   - 구버전 트래픽 비중이 높아 조회량이 요청 수에 비례해 늘면서
     커넥션 풀이 고갈되는 구조였습니다.
```

딱딱함과 늘어짐 사이의 배합이다. 한 문장에는 한 사실만 담는다 —
"~해서 ~했고 그 결과 ~했습니다"처럼 인과가 두 번 접히면 조치와 결과가 어긋나기 시작한다.

## 언제 쓰고, 언제 안 쓰는가

- **쓴다:** 포트폴리오 사례를 새로 쓸 때, 기존 사례를 5블록으로 재구성할 때,
  러프한 항목 나열을 읽히는 문서로 만들 때, 사례의 논리 구멍을 찾을 때.
- **안 쓴다:** 자기소개서 · 지원 동기, 이력서 전체 첨삭, PR/커밋 설명.
  이력서 한 줄로 **압축**하는 작업은 `improvement-case` 스킬이 맡는다.
  이 스킬은 포트폴리오 문서에서 **읽히는 구조**를 잡는다.
