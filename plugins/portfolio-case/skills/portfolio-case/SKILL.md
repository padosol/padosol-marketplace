  작업(improvement-case)이나 자기소개서 작성과는 다르다.

# 포트폴리오 문제해결 사례 작성

## 이 스킬이 지키려는 것

좋은 사례는 **소제목만 세로로 훑어도 전체가 추적된다.**

```
문제 1  간헐적 데드락        →  원인 1  비관적 락 사용
문제 2  매월 데드락          →  원인 2  다중 쿼리 결과
문제 3  수정 이후에도 발생    →  원인 3  쿼리 결과가 없는 경우
```

같은 번호는 **같은 대상**을 가리킨다. 대응이 맞아떨어지면 읽는 사람이 사례를 끝까지 따라오고,
어긋나면 **그 자리가 곧 논리 구멍**이다.

그래서 이 스킬은 본문을 바로 쓰지 않는다. **대응표를 먼저 세우고, 거기서 구멍을 잡은 뒤** 본문을 쓴다.

## 블록 구성 — 6블록, 이 순서

| 순서 | 블록 | 담는 것 |
|---|---|---|
| 1 | **문제** | 관측된 증상 |
| 2 | **원인** | 그 증상을 만든 구조 |
| 3 | **측정** | **해결 전** — 문제를 어떻게 재현·계측했나 |
| 4 | **해결** | 실제로 적용한 조치 |
| 5 | **평가** | **해결 후** — 어떤 환경에서 무엇을 확인했나 |
| 6 | **비고** | 검토했다가 **채택하지 않은 대안** |

**측정과 평가를 헷갈리지 않는다.** 측정은 해결 전에 문제를 손에 잡히게 만든 단계(재현 테스트,
계측)이고, 평가는 해결 후에 그것이 실제로 통했는지 확인한 단계다. 둘을 한 블록에 섞으면
"문제를 재현할 줄 알았다"와 "고친 걸 검증했다" 중 하나가 사라진다.

## 절대 규칙 — 지어내지 않는다

도구 이름 · 측정 조건 · 수치 · 확인 수단을 **추측으로 채우지 않는다.**
사용자가 말하지 않은 값은 `✍️` 마커로 남기고 질문한다.

```
    - JMeter로 실제 환경과 유사한 상황에서 정상 작동 여부를 확인합니다. (✍️ 동시 요청 수 확인 필요)
```

`✍️` 가 하나라도 남아 있으면 그 사례는 **미완성**이다. 완성했다고 보고하지 말고 남은 마커를 그대로 나열한다.

## 작업 절차

1. **재료 분해.** 사용자가 준 항목 · 메모 · 로그를 문장 단위로 쪼개 6블록 중 어디에 속하는지 배정한다.
   이 단계에서 **원인이 섞인 문제 문장**, **해결에 들어간 버린 대안**을 먼저 걷어낸다.

2. **대응표 확정.** 소제목만으로 아래 표를 만들어 **사용자에게 먼저 보여준다.**

   | | 1번 | 2번 | 3번 |
   |---|---|---|---|
   | 문제 | 간헐적 데드락 | 매월 데드락 | 수정 이후에도 발생 |
   | 원인 | 비관적 락 사용 | 다중 쿼리 결과 | 쿼리 결과가 없는 경우 |
   | 해결 | Redis 분산 락 | 월간 마일리지 로직 수정 | Redis 분산 락 |

   문제와 원인은 번호가 1:1로 붙는다. **해결은 하나가 여러 문제를 덮을 수 있다**(위 표의 1번·3번).
   그 경우 같은 조치를 두 번 쓰지 말고 해결 블록에 한 항목으로 두되, 대응표에서 어느 문제들을
   덮는지 확인한다. 빈 칸이 생기면 그게 질문 목록이다 — **빈 칸을 문장으로 덮지 말고 한 번에 모아서 묻는다.**

   측정 · 평가 · 비고는 번호 대응 대상이 아니다. 항목 수가 문제 수와 달라도 된다.

3. **본문 작성.** `assets/portfolio-template.md` 를 복사해 채운다. 포맷은 아래 "마크다운 포맷"을
   글자 그대로 지킨다. 블록별 상세 규칙과 표현 사전은 `references/block-rules.md` 를 따른다.

4. **검산.** `references/quality-gate.md` 의 6문항을 순서대로 통과시킨다.
   못 고친 항목은 `✍️` 로 남기고 사용자에게 보고한다.

## 마크다운 포맷 — 그대로 따른다

블록 제목은 `###`, 소제목은 **볼드**, 하위 내용은 **스페이스 4칸** 들여쓴 `-` 불릿이다.

**문제 · 원인 · 해결 — 번호 목록**

```markdown
### 문제

1. **간헐적 데드락**
    - 매일 12시에, Spring Boot와 JPA 환경에서 마일리지 서비스 운영 중 간헐적으로 데드락이 발생합니다.
    - 데드락은 일일 및 월별 마일리지 작업 중에 발생합니다.
2. **매월 데드락**
    - 매월 1일에, 마일리지 서비스 운영 중 데드락이 발생합니다.
```

**측정 · 평가 — 번호 없이, 볼드 소제목 + 들여쓰기 없는 불릿**

```markdown
### 측정

**데드락 재현**

- 테스트 코드를 사용하여 일일 및 월별 마일리지 테이블의 빈 칼럼에 대한 API를 동시에 요청하여 데드락을 재현합니다.
```

**비고 — 번호 없이, 불릿 소제목 + 4칸 들여쓴 불릿**

```markdown
### 비고

- **배치 서버 고려**
    - 매일 12시와 매월 1일에 배치 서버로 데이터를 삽입하는 방법을 고려하였으나, 삽입에 오랜 시간이 걸리고 해당 API의 트래픽이 많아 병목이 우려되어 다른 방안을 채택하였습니다.
```

| 위치 | 마커 | 소제목 | 하위 들여쓰기 |
|---|---|---|---|
| 문제 · 원인 · 해결 | `1.` `2.` `3.` | `**볼드**` | 스페이스 4칸 |
| 측정 · 평가 | 없음 | `**볼드**` 단독 줄 | 없음 (0칸) |
| 비고 | `-` | `**볼드**` | 스페이스 4칸 |

- 블록 제목 뒤, 그리고 측정·평가의 볼드 소제목 뒤에는 **빈 줄 한 줄**을 둔다.
- 탭을 쓰지 않는다. 들여쓰기는 항상 스페이스 4칸이다.
- 소제목 하나에 하위 불릿은 **1~3줄**. 넘으면 소제목을 쪼갤 신호다.
- 문장은 모두 **존댓말**로 끝낸다 — "~합니다", "~하였습니다".

## 소제목 규칙

| 규칙 | 내용 |
|---|---|
| 명사구로 끝낸다 | ✗ "데드락이 발생함" → ✓ "간헐적 데드락" |
| 4~15자로 압축한다 | 목차만 훑어도 무슨 사례인지 보이는 길이 |
| 블록별로 관점을 바꾼다 | 문제는 **증상**, 원인은 **구조**, 해결은 **조치**를 이름에 담는다 |

블록마다 관점이 바뀌어야 대응표가 정보를 준다.
문제도 "데드락", 원인도 "데드락"이면 한 칸이 낭비된다.

## 블록별 주어와 시제

| 블록 | 주어 | 시제 | 대표형 |
|---|---|---|---|
| 문제 | 사용자 / 시스템 | 현재형 | "~가 발생합니다" |
| 원인 | 코드 / 설정 / 쿼리 | 현재형 진행 | "~를 사용하고 있습니다" |
| 측정 | 나 / 테스트 | 현재형 | "~하여 재현합니다" |
| 해결 | 나 | 과거형 | "~하였습니다" |
| 평가 | 나 / 검증 | 현재형 | "~정상 작동 여부를 확인합니다" |
| 비고 | 나 | 과거형 | "~고려하였으나 ~채택하였습니다" |

**해결만 과거형이다.** 실제로 한 조치이기 때문이고, 나머지는 사례를 설명하는 시점의 현재형이다.

## 비고 — 버린 대안만 담는다

비고는 **검토했다가 채택하지 않은 대안**을 적는 자리다. 그 외의 것을 밀어 넣지 않는다.

```markdown
### 비고

- **배치 서버 고려**
    - 매일 12시와 매월 1일에 배치 서버로 데이터를 삽입하는 방법을 고려하였으나, 삽입에 오랜 시간이 걸리고 해당 API의 트래픽이 많아 병목이 우려되어 다른 방안을 채택하였습니다.
- **MySQL 분산 락 고려**
    - MySQL의 USER-LEVEL LOCK은 커넥션 부족이 우려되어 피하고, Redis를 도입하여 분산 락을 사용하였습니다.
```

- 항목은 **2~3개**, 각 하위 불릿은 **1~2줄**.
- 소제목은 `**~ 고려**` 형태가 기본이다.
- 한 항목 = 하나의 대안. "왜 검토했고, 왜 안 썼는지"가 한 문장에 들어간다.
- **한계 · 치른 대가 · 남은 과제 · 확장 적용 · 다음 단계를 늘어놓지 않는다.**
  비고가 길어지면 사례 전체가 변명처럼 읽힌다. 대안 검토 이력만 남기고 나머지는 버린다.

**버린 대안은 해결이 아니라 비고에 쓴다.** 해결 블록에는 실제로 적용한 조치만 남긴다.

## 언제 쓰고, 언제 안 쓰는가

- **쓴다:** 포트폴리오 문제해결 사례를 새로 쓸 때, 기존 사례를 6블록으로 재구성할 때,
  러프한 항목 나열을 읽히는 문서로 만들 때, 사례의 논리 구멍을 찾을 때.
- **안 쓴다:** 자기소개서 · 지원 동기, 이력서 전체 첨삭, PR/커밋 설명 작성.
  이력서 한 줄로 **압축**하는 작업은 `improvement-case` 스킬이 맡는다.
