# 예시 — 러프한 재료에서 완성 사례까지

받은 항목이 정리되지 않은 상태일 때 어떤 경로로 6블록이 되는지 보여준다.

---

## ① 사용자가 준 재료

> 마일리지 서비스에서 데드락이 자꾸 났음. 매일 12시랑 매월 1일에.
> 비관적 락 쓰는데 빈 row에 락 걸면 갭 락 생겨서 그런 거였고, 월간 쪽은 1년치 행을
> 다 가져와서 업데이트하는 레거시라 쿼리 여러 개 나가는 게 문제였음.
> 월간 로직 고쳤는데도 계속 나서 결국 Redis 분산 락 붙임. 배치 서버로 미리 데이터
> 넣어두는 것도 생각했는데 사용자 전체 넣으려니 너무 오래 걸리고 그 API 트래픽도 많아서 접음.
> MySQL 유저 레벨 락도 있는데 커넥션 모자랄까봐 안 씀. 테스트 코드로 동시 요청 때려서 재현했고
> 알파에서 JMeter로 확인함

한 덩어리에 여섯 블록이 뒤엉켜 있다. 먼저 **분해**한다.

| 재료 조각 | 배정 | 손볼 점 |
|---|---|---|
| 매일 12시·매월 1일 데드락 | 문제 1·2 | 두 개로 쪼갠다 |
| 월간 로직 고쳤는데도 계속 남 | **문제 3** | 해결 실패도 문제 항목이다 |
| 비관적 락 → 갭 락 | 원인 1 | 메커니즘을 단계로 편다 |
| 1년치 행 → 쿼리 여러 개 | 원인 2 | 넥스트 키 락까지 이어 쓴다 |
| 빈 row에 락 → 갭 락 | 원인 3 | — |
| 테스트 코드로 동시 요청 재현 | **측정** | 해결 앞에 온다 |
| 월간 로직·쿼리 수정 | 해결 1 | 기존 방식을 먼저 쓴다 |
| Redis 분산 락 | 해결 2 | 1번으로 부족했던 이유를 붙인다 |
| 알파에서 JMeter 확인 | **평가** | 측정과 다른 블록이다 |
| 배치 서버 생각했는데 접음 | **비고** | 해결이 아니라 비고 |
| MySQL 유저 레벨 락 안 씀 | **비고** | 해결이 아니라 비고 |

**대안 두 개가 비고로 빠지는 것**이 이 분해의 핵심이다.
"생각했는데 접음"은 실제로 한 조치가 아니므로 해결 블록에 남기지 않는다.

`JMeter 조건`, `동시 요청 수`는 재료에 없다. **지어내지 않고 묻는다.**

---

## ② 대응표 (본문보다 먼저 확정)

| | 1번 | 2번 | 3번 |
|---|---|---|---|
| 문제 | 간헐적 데드락 | 매월 데드락 | 수정 이후에도 발생 |
| 원인 | 비관적 락 사용 | 다중 쿼리 결과 | 쿼리 결과가 없는 경우 |
| 해결 | Redis 분산 락 | 월간 마일리지 로직 수정 | Redis 분산 락 |

세로로 훑어 확인한다. 1번 줄은 *일일 데드락 → 갭 락 경쟁 → 분산 락* 으로 이어지고,
2번 줄은 *월간 데드락 → 다중 쿼리 → 로직 수정* 으로 이어진다.
3번은 *로직 수정 후에도 발생 → 빈 결과 갭 락 → 분산 락* 이라 **해결 2번(Redis)이 1번과 3번을 함께 덮는다.**
같은 조치를 두 번 쓰지 않고, 해결 블록에는 한 항목으로 둔다. **대응 성립.**

## ③ 완성 본문

### 문제

1. **간헐적 데드락**
    - 매일 12시에, Spring Boot와 JPA 환경에서 마일리지 서비스 운영 중 간헐적으로 데드락이 발생합니다.
    - 데드락은 일일 및 월별 마일리지 작업 중에 발생합니다.
2. **매월 데드락**
    - 매월 1일에, 마일리지 서비스 운영 중 데드락이 발생합니다.
3. **비즈니스 로직 수정 이후에도 데드락 발생**
    - 월간 마일리지 로직을 수정하여 데드락 해결을 기대했지만, 이전보다 빈도만 줄었을 뿐 여전히 발생하였습니다.

### 원인

1. **비관적 락 사용**
    - 업데이트 쿼리 실행 중 비관적 락을 사용하고 있습니다.
    - 일일 마일리지의 경우, 갭 락을 사용하여 모든 트랜잭션이 동시에 락을 경쟁합니다.
    - 이로 인해 트랜잭션이 서로의 갭 락을 대기하다가 데드락 상황이 발생합니다.
2. **다중 쿼리 결과**
    - 월간 마일리지 작업은 여러 쿼리 결과를 포함하고 있어, 넥스트 키 락으로 인해 데드락이 발생할 가능성이 높습니다.
3. **쿼리 결과가 없는 경우**
    - 매일·매월 새로운 row가 추가되는 경우, 쿼리 결과가 없는 row에 락을 걸면 갭 락이 생겨 데드락 상황이 발생할 가능성이 높습니다.

### 측정

**데드락 재현**

- 테스트 코드를 사용하여 일일 및 월별 마일리지 테이블의 빈 칼럼에 대한 API를 동시에 요청하여 데드락을 재현합니다.

### 해결

1. **월간 마일리지 데드락**
    - 기존 레거시 코드에서는 해당 계정에 대한 1년치 행을 가져와 월별 마일리지를 업데이트하는 방식이었습니다.
    - 해당 로직과 쿼리를 수정하여 필요한 경우에만 처리하도록 변경하였습니다.
2. **Redis 분산 락 적용**
    - 1번 해결 방법을 적용했음에도 빈 데이터에 대해 비관적 락 사용 시 갭 락이 발생하기 때문에, Redis의 분산 락을 사용하였습니다.

### 평가

**테스트**

- 로컬에서 테스트 코드를 사용하여 확인한 후, 알파 환경에서 JMeter를 사용하여 실제 환경과 유사한 상황에서(매월 12시 최대 요청 수) 정상 작동 여부를 확인합니다.

### 비고

- **배치 서버 고려**
    - 매일 12시와 매월 1일에 배치 서버를 통해 월별 마일리지 데이터를 삽입하는 방법을 고려하였으나, 모든 사용자에 대해 삽입하는 데 오랜 시간이 걸리고 해당 API의 트래픽이 많아서 병목 현상이 발생할 우려가 있어 다른 방안을 채택하였습니다.
- **MySQL 분산 락 고려**
    - MySQL의 USER-LEVEL LOCK은 커넥션 연결 부족 우려로 인해 피하고, Redis를 도입하여 분산 락을 사용하였습니다.

## ④ 이 예시에서 눈여겨볼 것

**비고가 두 항목, 각 한 줄이다.** 남은 한계("분산 락이라 Redis 장애 시…"), 치른 대가
("인프라가 하나 늘었다"), 다음 과제 같은 것을 적고 싶어지지만 **전부 넣지 않는다.**
비고에는 검토했다가 버린 대안만 남긴다.

**측정과 평가가 해결을 사이에 두고 나뉘어 있다.** 측정은 고치기 전 재현(테스트 코드, 동시 요청),
평가는 고친 뒤 검증(로컬 → 알파, JMeter). 둘을 한 블록에 합치면
"재현할 줄 안다"와 "검증했다" 중 하나가 사라진다.

**문제 3번이 실패한 시도다.** 숨기지 않고 문제 항목으로 세운 덕분에,
해결이 왜 두 단계인지가 설명된다.
