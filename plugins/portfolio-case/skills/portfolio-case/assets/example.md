# 예시 — 러프한 재료에서 완성 사례까지

받은 항목이 정리되지 않은 상태일 때 어떤 경로로 5블록이 되는지 보여준다.

---

## ① 사용자가 준 재료

> 로그인이 자꾸 풀린다는 문의가 많았는데 세션이 서버 메모리에 있어서 그런 거였음.
> 레디스로 옮겼더니 해결. 그리고 구버전 앱 트래픽 때문에 리다이렉트 API가 느렸는데
> 매번 DB 조회해서 그랬고 캐시 붙여서 3초 걸리던 게 훨씬 빨라짐

문장 세 개에 다섯 블록이 뒤엉켜 있다. 먼저 **분해**한다.

| 재료 조각 | 배정 | 손볼 점 |
|---|---|---|
| 로그인이 자꾸 풀린다는 문의 | 문제 1 | — |
| 세션이 서버 메모리에 있어서 | **원인 1** | 문제 문장에 섞여 있었다 |
| 레디스로 옮김 | 해결 1 | 버린 대안이 없다 → 질문 |
| 리다이렉트 API가 느림 | 문제 2 | — |
| 매번 DB 조회 | 원인 2 | 확인 수단이 없다 → 질문 |
| 캐시 붙임 | 해결 2 | 어떤 캐시인지 없다 → 질문 |
| 3초 걸리던 게 | **측정 2** | 문제가 아니라 측정 자리의 수치다 |
| 훨씬 빨라짐 | 측정 2 | 형용사 → 숫자 필요 |

`세션 유실이 몇 건이었는지`, `무슨 도구로 쟀는지`는 재료에 없다. **지어내지 않고 묻는다.**

---

## ② 대응표 (본문보다 먼저 확정)

| | 1번 | 2번 |
|---|---|---|
| 문제 | 간헐적 로그인 끊김 | 응답 지연 및 요청 실패 |
| 원인 | 인스턴스 로컬 세션 저장 | 리다이렉트당 단건 조회 |
| 해결 | 세션 저장소 외부화 | 로컬 캐시 적용 |
| 측정 | 세션 유실 문의 건수 | 평균 응답 시간, 조회 호출 수 |

세로로 훑어 확인한다. 1번 줄은 *끊김 → 로컬 저장 → 외부화 → 유실 문의* 로 한 대상을 따라간다.
2번 줄도 *지연 → 단건 조회 → 캐시 → 응답 시간* 으로 이어진다. **대응 성립.**

---

## ③ 완성 본문

### 문제

1. 간헐적 로그인 끊김
   - 로그인한 사용자가 타임아웃 전인데도 간헐적으로 로그인이 끊기는 현상이 발생
   - 재로그인하면 정상 동작해 재현 조건이 불명확한 상태로 문의가 누적

2. 응답 지연 및 요청 실패
   - 구버전 앱 요청이 몰리는 시간대에 API 응답이 지연
   - 일부 요청은 타임아웃으로 실패

### 원인

1. 인스턴스 로컬 세션 저장
   - 세션이 각 인스턴스의 로컬 메모리에 저장되고 있었습니다.
   - 로드밸런서가 요청마다 다른 인스턴스로 분배하면서,
     세션이 없는 인스턴스로 향한 요청이 로그인 만료로 처리됐습니다.

2. 리다이렉트당 단건 조회
   - 실행 계획 확인 결과 리다이렉트 처리마다 UUID 단건 조회가 발생하고 있었습니다.
   - 구버전 트래픽 비중이 높아 조회량이 요청 수에 비례해 늘면서
     커넥션 풀이 고갈됐습니다.

### 해결

1. 세션 저장소 외부화
   - 세션 저장소를 Redis로 분리해 인스턴스 간 세션을 공유하도록 변경했습니다.
   - 로드밸런서 스티키 세션도 검토했으나 인스턴스 증설 시 부하가 쏠려
     저장소 분리를 선택했습니다.

2. 로컬 캐시 적용
   - Caffeine 기반 로컬 캐시를 적용하고 최대 엔트리 수와 TTL을 설정했습니다.
   - 분산 캐시도 검토했으나 공유 메모리 인프라가 없는 환경이라
     인스턴스별 로컬 캐시로 결정했습니다.

### 측정

1. 세션 유실 문의
   - 배포 후 4주간 세션 유실 관련 문의 주 12건 → 0건

2. 응답 시간 및 조회 호출 수
   - k6로 동일 시나리오(가상 사용자 100, 5분) 부하 테스트 결과
     평균 응답 시간 820ms → 95ms
   - DB 조회 호출 수 요청당 1회 → 0.03회

### 비고

1. 캐시 정합성 한계
   - 인스턴스별 캐시라 갱신 시점이 서버마다 달라질 수 있어,
     변경 빈도가 낮은 데이터에만 적용했습니다.
   - 트래픽이 더 늘면 공유 캐시로 전환이 필요합니다.

2. 확장 적용
   - 이후 동일 패턴의 조회 3곳에 같은 방식을 적용했습니다.

---

## ④ 재료에 없어서 물었던 것

완성본의 아래 값들은 **재료에 없었고, 사용자에게 물어서 채운 것**이다. 임의로 만들지 않는다.

| 채워진 값 | 던진 질문 |
|---|---|
| 주 12건 → 0건 | 세션 유실 문의가 얼마나 들어왔고, 이후 어떻게 됐나요? |
| k6, 가상 사용자 100·5분 | 응답 시간은 무슨 도구로 어떤 조건에서 쟀나요? |
| 820ms → 95ms | "3초"는 최대치인가요 평균인가요? |
| 스티키 세션 / 분산 캐시 | Redis와 Caffeine을 고를 때 함께 검토한 대안이 있었나요? |

재료의 "3초"가 완성본에서 **820ms** 로 바뀐 데 주목한다.
러프한 기억 속 숫자는 대개 체감값이라, 측정 조건을 물으면 실제 수치가 따라 나온다.
