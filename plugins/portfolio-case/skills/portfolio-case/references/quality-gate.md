# 포맷 · 문체 · 안티패턴 · 검산

---

## 1. 포맷 점검

제출 전에 눈으로 확인한다. 하나라도 어긋나면 문서 전체가 흐트러져 보인다.

- [ ] 블록 제목이 `### 문제` `### 원인` `### 측정` `### 해결` `### 평가` `### 비고` 6개, **이 순서**인가
- [ ] 문제 · 원인 · 해결은 `1.` `2.` 번호 목록인가
- [ ] 측정 · 평가는 번호 없이 `**볼드 소제목**` 단독 줄 + 빈 줄 + 들여쓰기 없는 불릿인가
- [ ] 비고는 `- **볼드 소제목**` + 4칸 들여쓴 불릿인가
- [ ] 하위 불릿 들여쓰기가 **스페이스 4칸**인가 (탭 아님)
- [ ] 모든 문장이 존댓말(`~합니다` / `~하였습니다`)로 끝나는가

```markdown
### 문제

1. **간헐적 데드락**
    - 매일 12시에, 마일리지 서비스 운영 중 간헐적으로 데드락이 발생합니다.

### 측정

**데드락 재현**

- 테스트 코드를 사용하여 API를 동시에 요청하여 데드락을 재현합니다.

### 비고

- **배치 서버 고려**
    - 배치 서버로 삽입하는 방법을 고려하였으나, 병목이 우려되어 다른 방안을 채택하였습니다.
```

## 2. 문체

### 한 문장에 한 사실만

"~해서 ~했고 그 결과 ~했습니다"처럼 **인과가 두 번 이상 접히면** 조치와 결과가 어긋나기 시작한다.
문장을 끊는 것만으로 논리 오류가 드러난다.

예외는 비고다. 비고는 **대안 + 버린 이유 + 대신 택한 것**을 한 문장에 담는다 — 항목을 짧게 유지하기 위해서다.

### 볼드는 소제목에만

본문 문장 안에서는 볼드를 쓰지 않는다. 소제목이 이미 볼드라, 본문까지 굵어지면 목차 기능이 사라진다.

### 길이

- 소제목당 하위 불릿은 **1~3줄**. 넘으면 소제목을 쪼갤 신호다.
- 넘친다면 대개 **배경 설명이 문제 · 원인 블록에 스며든 것**이다.
- 비고만 예외적으로 더 짧다 — 항목당 **1~2줄**.

### 시제

해결과 비고만 과거형(`~하였습니다`), 나머지는 현재형(`~합니다`)이다.
해결·비고는 실제로 한 일이고, 나머지는 사례를 설명하는 시점의 서술이기 때문이다.

## 3. 안티패턴

| 쓰지 말 것 | 왜 |
|---|---|
| 소제목 없이 불릿만 나열 | 목차로 훑을 수 없고, 블록 간 대응 검사도 못 한다 |
| 문제 블록에 원인 섞기 | "갭 락 때문에 데드락 발생" — 원인과 결과가 뒤섞여 어느 쪽도 검증 불가 |
| 문제 블록에 수치 쓰기 | 평가 블록이 할 말을 잃는다 |
| 측정과 평가를 한 블록에 | "재현할 줄 안다"와 "고친 걸 검증했다" 중 하나가 사라진다 |
| 측정을 해결 뒤에 두기 | 재현은 고치기 **전에** 하는 일이다. 순서가 뒤집히면 흐름이 깨진다 |
| 원인에 추측성 표현 | "~로 추정됩니다" — 규명이 덜 된 채 조치했다는 인상 |
| 해결에 "최적화하였습니다" 단독 | 대상과 방향이 없으면 정보량 0 |
| **해결에 버린 대안 쓰기** | 실제로 한 것과 안 한 것이 섞인다. 대안은 비고로 |
| **비고에 한계·대가·다음 과제 늘어놓기** | 사례가 변명처럼 읽힌다. 비고는 버린 대안만 |
| 비고 항목이 4개 이상이거나 3줄 넘김 | 읽는 사람이 본론을 잊는다 |
| 평가에 "대폭 향상" | 조건 없는 형용사는 숫자가 아니다 |
| 본문 문장에 볼드 남발 | 소제목의 목차 기능이 사라진다 |

## 4. 최종 점검 6문항

작성 후 이 **순서대로** 검산한다.

- [ ] 1. 6블록이 `문제 → 원인 → 측정 → 해결 → 평가 → 비고` 순서로 있고, **소제목만 읽어도 흐름이 잡히는가**
- [ ] 2. **문제 N번과 원인 N번이 같은 대상을 가리키고, 각 문제가 어느 해결로 이어지는지 추적되는가**
- [ ] 3. 문제 블록에 원인이 섞여 있지 않은가
- [ ] 4. 측정은 **해결 전 재현**, 평가는 **해결 후 검증**으로 나뉘어 있는가
- [ ] 5. **비고에 버린 대안만 있고**(한계·대가·다음 과제 없이), 항목 2~3개에 각 1~2줄인가
- [ ] 6. 측정과 평가에 **도구와 조건**이 있는가

### 2번이 핵심 장치다

조치와 결과의 불일치를 잡는 자리다. **소제목만 세로로 훑어보면 대부분 걸러진다.**

```
문제 1  간헐적 데드락
원인 1  비관적 락 사용        ← 데드락의 구조적 이유인가?     ✓
해결 2  Redis 분산 락 적용    ← 그 구조를 바꾸는가?           ✓
```

해결은 하나가 여러 문제를 덮을 수 있다(위에서 해결 2번이 문제 1번과 3번을 함께 덮는다).
다만 **어느 문제도 해결로 이어지지 않으면** 그 자리가 구멍이다 — 고치지 않았거나, 문제 항목이 과장된 것이다.

### 자주 걸리는 항목

- **5번** — 가장 자주 걸린다. 비고에 한계와 다음 과제를 적고 싶어지는데, 전부 지운다.
- **4번** — 재현(측정)과 검증(평가)을 한 덩어리로 쓰면 여기서 걸린다.
- **6번** — 도구는 썼는데 조건(동시 요청 수, 환경)이 빠지는 경우가 많다. 모르면 `✍️` 로 묻는다.

### 검산 후 보고

`✍️` 마커가 남았는데 "완성했습니다"라고 보고하지 않는다.
남은 마커를 그대로 나열하고, 무엇을 물어야 채워지는지 함께 말한다.
