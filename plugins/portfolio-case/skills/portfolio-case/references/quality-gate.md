# 문체 · 안티패턴 · 검산

---

## 1. 문체 — 개조식과 서술의 배합

딱딱함을 피하면서 늘어지지 않는 배합은 하나다.

> **소제목은 명사형, 첫 내용은 개조식, 부연은 서술형 한 문장.**

```
### 원인

1. 리다이렉트당 단건 조회
   - 리다이렉트 처리마다 UUID 단건 조회가 발생.
   - 구버전 트래픽 비중이 높아 조회량이 요청 수에 비례해 늘면서
     커넥션 풀이 고갈되는 구조였습니다.
```

### 한 문장에 한 사실만

"~해서 ~했고 그 결과 ~했습니다"처럼 **인과가 두 번 이상 접히면** 조치와 결과가 어긋나기 시작한다.
문장을 끊는 것만으로 논리 오류가 드러난다.

### 길이

- 소제목당 내용은 **3줄을 넘기지 않는다.**
- 넘친다면 대개 **배경 설명이 문제 · 원인 블록에 스며든 것**이다.
  배경이 꼭 필요하면 사례 제목 아래 **"상황" 한 줄**로 빼고 5블록은 건드리지 않는다.
- 내용이 계속 늘어나면 소제목을 **쪼갤 신호**다.

### 볼드

- 문장 전체를 볼드 처리하지 않는다.
- **판단이 걸린 지점**에만 — 수치, 핵심 기술 용어, 인과의 연결점.
- 한 항목에 볼드가 3군데를 넘으면 강조가 사라진다.

## 2. 안티패턴

| 쓰지 말 것 | 왜 |
|---|---|
| 소제목 없이 불릿만 나열 | 목차로 훑을 수 없고, 블록 간 대응 검사도 못 한다 |
| 문제 블록에 원인 섞기 | "캐시가 없어서 장애가 발생" — 원인과 결과가 뒤섞여 어느 쪽도 검증 불가 |
| 문제 블록에 수치 쓰기 | 측정 블록이 할 말을 잃는다 |
| 원인에 추측성 표현 | "~로 보입니다" — 규명이 덜 된 채 조치했다는 인상 |
| 해결에 "최적화했습니다" 단독 | 대상과 방향이 없으면 정보량 0 |
| 해결에 버린 대안이 없음 | 기술 나열은 누구나 한다. 선택 이유가 경험의 증거다 |
| 측정에 "대폭 향상" | 조건 없는 형용사는 숫자가 아니다 |
| 측정 조건 누락 | "그 3초는 어떤 조건이죠?" 한 방에 무너진다 |
| 비고 비움 | 트레이드오프를 모르는 사람으로 보인다 |
| 블록 간 번호 어긋남 | 문제 1번의 답이 해결 2번에 있으면 독자가 사례를 놓친다 |

## 3. 최종 점검 6문항

작성 후 이 **순서대로** 검산한다.

- [ ] 1. 블록마다 소제목이 붙어 있고, **소제목만 읽어도 흐름이 잡히는가**
- [ ] 2. **문제 1번 — 원인 1번 — 해결 1번 — 측정 1번이 같은 대상을 가리키는가**
- [ ] 3. 문제 블록에 원인이 섞여 있지 않은가
- [ ] 4. 원인에 **무엇을 보고 알았는지**가 있고, 추측성 표현 없이 단정형인가
- [ ] 5. 해결에 **선택하지 않은 대안**이 한 줄이라도 있는가
- [ ] 6. 측정에 **도구와 조건**이 있는가

### 2번이 핵심 장치다

조치와 결과의 불일치를 잡는 자리다. **소제목만 세로로 훑어보면 대부분 걸러진다.**

```
문제 1  간헐적 로그인 끊김
원인 1  인스턴스 로컬 세션 저장     ← 끊김의 구조적 이유인가?  ✓
해결 1  세션 저장소 외부화          ← 그 구조를 바꾸는가?      ✓
측정 1  세션 유실 문의 건수         ← 문제 1의 증상을 재는가?  ✓
```

측정 1번이 "평균 응답 시간"이었다면 여기서 걸린다.
로그인 끊김을 고쳤는데 응답 시간을 재고 있다면, 둘 중 하나는 다른 사례의 것이다.

### 자주 걸리는 항목

- **5번** — 가장 자주 빠진다. 조치만 쓰고 대안을 안 쓰면 "그 기술을 왜 골랐냐"에서 멈춘다.
- **6번** — 수치를 쓴 사례는 대부분 여기서 걸린다. 모르면 지어내지 말고 `✍️` 로 묻는다.
- **3번** — "때문에 / 탓에 / 미흡하여"를 문제 블록에서 검색하면 기계적으로 잡힌다.
