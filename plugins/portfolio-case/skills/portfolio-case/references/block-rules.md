# 블록별 작성 규칙

SKILL.md 의 골격을 실제 문장으로 만드는 방법. 예시는 모두 실제 사례에서 뽑은 것이고,
포맷(번호·볼드·4칸 들여쓰기)은 예시 그대로 따른다.

---

## 문제 — 관측된 증상만

원인 암시는 금지다. **"때문에", "탓에", "미흡하여"** 가 들어가면 그 문장은 원인 블록으로 옮긴다.

```markdown
### 문제

1. **간헐적 데드락**
    - 매일 12시에, Spring Boot와 JPA 환경에서 마일리지 서비스 운영 중 간헐적으로 데드락이 발생합니다.
    - 데드락은 일일 및 월별 마일리지 작업 중에 발생합니다.
2. **매월 데드락**
    - 매월 1일에, 마일리지 서비스 운영 중 데드락이 발생합니다.
3. **비즈니스 로직 수정 이후에도 데드락 발생**
    - 월간 마일리지 로직을 수정하여 데드락 해결을 기대했지만, 이전보다 빈도만 줄었을 뿐 여전히 발생하였습니다.
```

**언제 · 어떤 환경인지 앞에 붙인다.** "매일 12시에", "매월 1일에", "Spring Boot와 JPA 환경에서" —
재현 조건이 보이면 문제가 손에 잡힌다.

**한 번 고쳤는데 또 났다면 그것도 문제 항목이다.** 위 3번처럼 쓰면 원인이 하나가 아니었다는
사실이 드러나고, 뒤의 해결이 두 단계로 나뉜 이유가 설명된다. 실패한 시도를 숨기지 않는다.

**쓰는 표현**

`~가 발생합니다` · `~중에 발생합니다` · `~하였습니다`(이미 끝난 시도의 결과)

**여기에 원인과 수치를 쓰지 않는다**

"갭 락 때문에"는 원인 블록, "3초 걸림"은 평가 블록의 몫이다.

---

## 원인 — 구조를 지목한다

증상이 아니라 **그 증상을 만든 구조**를 쓴다. 무엇을 보고 알았는지(실행 계획, 로그, 덤프)가 있으면 함께 붙인다.

```markdown
### 원인

1. **비관적 락 사용**
    - 업데이트 쿼리 실행 중 비관적 락을 사용하고 있습니다.
    - 일일 마일리지의 경우, 갭 락을 사용하여 모든 트랜잭션이 동시에 락을 경쟁합니다.
    - 이로 인해 트랜잭션이 서로의 갭 락을 대기하다가 데드락 상황이 발생합니다.
2. **다중 쿼리 결과**
    - 월간 마일리지 작업은 여러 쿼리 결과를 포함하고 있어, 넥스트 키 락으로 인해 데드락이 발생할 가능성이 높습니다.
3. **쿼리 결과가 없는 경우**
    - 매일·매월 새로운 row가 추가되는 경우, 쿼리 결과가 없는 row에 락을 걸면 갭 락이 생겨 데드락 상황이 발생할 가능성이 높습니다.
```

**메커니즘을 한 단계씩 이어 쓴다.** 위 1번은 *비관적 락 → 갭 락 → 경쟁 → 대기 → 데드락* 으로
세 줄에 걸쳐 이어진다. "락 때문입니다"에서 멈추지 않는다.

### 추측과 조건부 서술을 구분한다

원인 **규명이 덜 된 것**은 쓰지 않지만, **조건이 맞을 때 발생하는 성질**은 그대로 써도 된다.

| 구분 | 예 | 판정 |
|---|---|---|
| 규명 불확실 | "데드락의 원인은 락 경합으로 추정됩니다" | ✗ 무엇을 확인했는지 없다 |
| 조건부 발생 | "쿼리 결과가 없는 row에 락을 걸면 갭 락이 생겨 데드락이 발생할 가능성이 높습니다" | ✓ 구조는 확정, 발생이 조건부일 뿐 |

앞은 "아직 모른다"는 뜻이고, 뒤는 "구조는 알고 있고 그 구조가 확률적으로 터진다"는 뜻이다.

**쓰지 않는 표현**

`~로 추정됩니다` · `~때문인 것 같습니다` · `~일 수도 있습니다`(구조 자체가 불확실할 때)

## 측정 — 해결 전에 문제를 손에 잡히게 만든 단계

**해결보다 먼저 온다.** 재현하지 못한 문제는 고쳤는지도 알 수 없으므로, 재현·계측 방법을 여기 쓴다.

```markdown
### 측정

**데드락 재현**

- 테스트 코드를 사용하여 일일 및 월별 마일리지 테이블의 빈 칼럼에 대한 API를 동시에 요청하여 데드락을 재현합니다.
```

- 번호를 붙이지 않는다. **볼드 소제목 한 줄 + 빈 줄 + 들여쓰기 없는 불릿**이다.
- 항목은 보통 하나면 충분하다. 재현 경로가 둘 이상일 때만 소제목을 늘린다.
- **무엇으로 · 어떤 조건에서** 재현했는지를 한 문장에 담는다
  (테스트 코드 / 동시 요청 / 빈 칼럼 대상 — 세 가지가 다 들어 있다).

재현하지 못했다면 그 사실을 쓰고, 대신 무엇을 보고 문제를 특정했는지 적는다
(운영 로그, 슬로우 쿼리 로그, 스레드 덤프). **재현했다고 지어내지 않는다.**

## 해결 — 실제로 적용한 조치만

**검토했다가 버린 대안은 여기 쓰지 않는다.** 그건 비고로 간다. 해결 블록은 실제로 한 것만 남긴다.

```markdown
### 해결

1. **월간 마일리지 데드락**
    - 기존 레거시 코드에서는 해당 계정에 대한 1년치 행을 가져와 월별 마일리지를 업데이트하는 방식이었습니다.
    - 해당 로직과 쿼리를 수정하여 필요한 경우에만 처리하도록 변경하였습니다.
2. **Redis 분산 락 적용**
    - 1번 해결 방법을 적용했음에도 빈 데이터에 대해 비관적 락 사용 시 갭 락이 발생하기 때문에, Redis의 분산 락을 사용하였습니다.
```

**기존 방식 → 바꾼 방식** 순으로 쓰면 조치의 크기가 보인다(위 1번).
바꾼 것만 쓰면 리뷰어는 원래 어땠는지 모른다.

**앞 조치로 부족했던 이유를 다음 조치에 붙인다**(위 2번). 이 한 줄이 있어야 조치가 두 개인 이유가 설명된다.

**쓰는 표현**

`~하도록 변경하였습니다` · `~를 사용하였습니다` · `~를 적용하였습니다` · `~에도 불구하고 ~때문에 ~하였습니다`

**피할 표현**

`최적화하였습니다`(무엇을?) · `개선하였습니다`(어떻게?) — 단독으로 쓰면 정보량이 0이다.

## 평가 — 해결 후 검증

측정이 "고치기 전에 재현한 것"이라면, 평가는 **"고친 뒤 확인한 것"** 이다.

```markdown
### 평가

**테스트**

- 로컬에서 테스트 코드를 사용하여 확인한 후, 알파 환경에서 JMeter를 사용하여 실제 환경과 유사한 상황에서(매월 12시 최대 요청 수) 정상 작동 여부를 확인합니다.
```

- 측정과 같은 포맷이다. 번호 없이 볼드 소제목 + 들여쓰기 없는 불릿.
- **어디서 · 무엇으로 · 어떤 조건에서** 확인했는지를 담는다
  (로컬 → 알파 환경 / 테스트 코드 → JMeter / 매월 12시 최대 요청 수).
- 단계가 있으면 순서대로 이어 쓴다 — 로컬에서 먼저, 그다음 실제와 유사한 환경에서.

**수치가 있으면 여기에 쓴다.** `평균 응답 820ms → 95ms` 처럼 before → after 를 남기되,
**측정 조건을 반드시 함께** 적는다. 수치가 없으면 억지로 만들지 말고
"어떤 환경에서 정상 동작을 확인했다"로 충분하다.

**피할 표현**

`대폭` · `크게` · `눈에 띄게` — 조건 없는 형용사는 숫자가 아니다.

## 비고 — 검토했다가 버린 대안만

이 블록에는 **채택하지 않은 대안**만 들어간다. 다른 것을 밀어 넣지 않는다.

```markdown
### 비고

- **배치 서버 고려**
    - 매일 12시와 매월 1일에 배치 서버를 통해 월별 마일리지 데이터를 삽입하는 방법을 고려하였으나, 모든 사용자에 대해 삽입하는 데 오랜 시간이 걸리고 해당 API의 트래픽이 많아서 병목 현상이 발생할 우려가 있어 다른 방안을 채택하였습니다.
- **MySQL 분산 락 고려**
    - MySQL의 USER-LEVEL LOCK은 커넥션 연결 부족 우려로 인해 피하고, Redis를 도입하여 분산 락을 사용하였습니다.
```

### 지켜야 할 분량

| 항목 | 기준 |
|---|---|
| 항목 수 | **2~3개** |
| 항목당 하위 불릿 | **1~2줄** |
| 소제목 형태 | `**~ 고려**` 가 기본 |

### 한 항목에 담기는 것

**대안 + 버린 이유 + 대신 택한 것** — 이 세 가지가 한 문장에 들어간다.

> MySQL의 USER-LEVEL LOCK은 **커넥션 연결 부족 우려로 인해** 피하고, **Redis를 도입하여** 분산 락을 사용하였습니다.

버린 이유가 없으면 그냥 기술 나열이다. **왜 안 썼는지가 이 블록의 전부**다.

### 넣지 않는 것

| 넣지 말 것 | 어떻게 |
|---|---|
| 남은 한계 · 못 막는 것 | 쓰지 않는다 (사례가 변명처럼 읽힌다) |
| 치른 대가 · 비용 증가 | 쓰지 않는다 |
| 미확인 구간 · 다음 과제 | 쓰지 않는다 |
| 확장 적용 이력 | 쓰지 않는다 |
| 원인을 특정 못 한 영역 | 원인 블록에서 확인된 범위까지만 쓰고 끝낸다 |

비고가 길어지면 사례 전체가 변명처럼 읽힌다. **대안 검토 이력만 남기고 나머지는 버린다.**
