# 블록별 작성 규칙

SKILL.md 의 골격을 실제 문장으로 만드는 방법. 각 블록마다 **쓰는 표현 / 쓰지 않는 표현**을 붙였다.

---

## 문제 — 관측된 증상만

원인 암시는 금지다. **"때문에", "탓에", "미흡하여"** 가 들어가면 그 문장은 원인 블록으로 옮긴다.

```
1. 간헐적 로그인 끊김
   - 로그인한 사용자가 타임아웃 전인데도 간헐적으로 로그인이 끊기는 현상이 발생
   - 재로그인하면 정상 동작해 재현 조건이 불명확한 상태로 문의가 누적

2. 응답 지연 및 요청 실패
   - 구버전 앱 요청이 몰리는 시간대에 API 응답이 지연
   - 일부 요청은 타임아웃으로 실패
```

**나쁜 예**

> 캐시가 없어서 DB 부하가 커져 장애가 발생했습니다

원인("캐시가 없어서")과 결과가 한 문장에 뒤섞였다. 캐시 부재는 원인 블록, 장애는 문제 블록이다.

**쓰는 표현**

`~현상 발생` · `~가 접수됨` · `~시 ~가 지연됨` · `~가 간헐적으로 실패함`

**여기에 수치를 쓰지 않는다**

"3초 걸림"을 문제에 쓰면 측정 블록이 할 말을 잃는다. 느리다는 **사실**만 쓰고, 숫자는 측정에서 낸다.

---

## 원인 — 확인한 사실 → 확정된 원인

**단정형**으로 쓴다. 무엇을 보고 알았는지(실행 계획, 로그, 스레드 덤프, 프로파일링)를 근거로 붙이면
단정이 근거를 갖는다.

```
1. 인스턴스 로컬 세션 저장
   - 세션이 각 인스턴스의 로컬 메모리에 저장되고 있었습니다.
   - 로드밸런서가 요청마다 다른 인스턴스로 분배하면서,
     세션이 없는 인스턴스로 향한 요청이 로그인 만료로 처리됐습니다.

2. 리다이렉트당 단건 조회
   - 실행 계획 확인 결과 리다이렉트 처리마다 UUID 단건 조회가 발생하고 있었습니다.
   - 구버전 트래픽 비중이 높아 조회량이 요청 수에 비례해 늘면서
     커넥션 풀이 고갈됐습니다.
```

**쓰는 표현**

`~를 확인한 결과 ~였습니다` · `~가 직접적인 원인이었습니다` · `~로 인해 ~가 발생하고 있었습니다` ·
`~는 ~에 의해 유발된 2차 증상이었습니다`

**쓰지 않는 표현**

`~로 추정됩니다` · `~로 보입니다` · `~일 가능성이 있습니다` · `~때문인 것 같습니다`

원인을 확실히 파악했기 때문에 해결할 수 있었던 것이다.
추측성 표현이 남아 있으면 **규명이 덜 된 채 조치했다는 인상**을 준다.

### 한 단계 더 파고든다

같은 사실이라도 메커니즘까지 내려간 쪽이 훨씬 낫다.

- 얕음: "UUID 조회가 많았습니다"
- 깊음: "리다이렉트마다 UUID로 단건 조회가 발생했고, 구버전 트래픽 비중이 높아
  조회량이 요청 수에 비례해 증가했습니다"

### 확인하지 못한 부분이 남았다면

원인 블록에서 흐리지 말고, **확인된 범위까지만 단정한 뒤 미확인 영역은 비고로 뺀다.**
그래야 원인 블록의 모든 문장을 단정형으로 유지할 수 있다.

```
원인  1. 요청 스레드 점유
         - 스레드 덤프 확인 결과 후처리 작업이 요청 스레드를 점유해
           톰캣 스레드 풀이 고갈됐습니다.

비고  1. 미확인 구간
         - 특정 파일 형식에서만 후처리 시간이 길어지는 부분은
           원인을 특정하지 못해 별도 과제로 분리했습니다.
```

이렇게 두면 "원인을 모른다"가 아니라
**"어디까지 규명했고 어디부터가 다음 과제인지 구분할 줄 안다"** 로 읽힌다.

## 해결 — 동사로 시작하고, 버린 대안을 한 줄 붙인다

기술 나열은 누구나 한다. **선택의 이유는 겪어본 사람만 쓴다.**

```
1. 세션 저장소 외부화
   - 세션 저장소를 Redis로 분리해 인스턴스 간 세션을 공유하도록 변경했습니다.
   - 로드밸런서 스티키 세션도 검토했으나 인스턴스 증설 시 부하가 쏠려
     저장소 분리를 선택했습니다.

2. 로컬 캐시 적용
   - Caffeine 기반 로컬 캐시를 적용하고 최대 엔트리 수와 TTL을 설정했습니다.
   - 분산 캐시도 검토했으나 공유 메모리 인프라가 없는 환경이라
     인스턴스별 로컬 캐시로 결정했습니다.
```

**쓰는 표현**

`~를 적용했습니다` · `~를 ~로 분리했습니다` · `~를 도입해 ~하도록 변경했습니다` ·
`A도 검토했으나 ~ 제약으로 B를 선택했습니다`

**피할 표현**

`최적화했습니다`(무엇을?) · `개선했습니다`(어떻게?) · `리팩터링했습니다`(어느 방향으로?)

단독으로 쓰면 정보량이 0이다. 대상과 방향을 붙여야 문장이 산다.

## 측정 — 무엇을 / 어떤 도구로 / 어떤 조건에서

수치만 던지지 않는다. 세 가지를 함께 붙인다.

```
1. 세션 유실 문의
   - 배포 후 4주간 세션 유실 관련 문의 주 12건 → 0건

2. 응답 시간 및 조회 호출 수
   - k6로 동일 시나리오(가상 사용자 100, 5분) 부하 테스트 결과
     평균 응답 시간 820ms → 95ms
   - DB 조회 호출 수 요청당 1회 → 0.03회
```

**나쁜 예**

> 성능이 대폭 향상되었습니다

**피할 표현**

`대폭` · `크게` · `눈에 띄게` · `획기적으로` — 전부 삭제하고 숫자로 대체한다.

### 수치를 아직 내지 못했다면

변명형 문장 대신, **확인한 사실만 단정형으로 남기고 계획을 덧붙인다.**

- 수정 전: 정량 수치는 없으나, 슬로우 쿼리 로그에서 해당 쿼리가 사라진 것으로 확인했습니다
- 수정 후: 배포 후 동일 시간대 슬로우 쿼리 로그에서 해당 쿼리가 사라졌습니다.
  부하 테스트 기반 정량 측정은 k6로 진행 예정입니다

사용자가 측정 도구나 조건을 말하지 않았다면 **지어내지 말고 `✍️` 로 남겨 묻는다.**

## 비고 — 한계와 트레이드오프

비어 있으면 "운 좋게 됐다"로 읽히고, 채워져 있으면 "구조를 이해하고 있다"로 읽힌다.

```
1. 캐시 정합성 한계
   - 인스턴스별 캐시라 갱신 시점이 서버마다 달라질 수 있어,
     변경 빈도가 낮은 데이터에만 적용했습니다.
   - 트래픽이 더 늘면 공유 캐시로 전환이 필요합니다.

2. 확장 적용
   - 이후 동일 패턴의 조회 3곳에 같은 방식을 적용했습니다.
```

들어갈 수 있는 것:

| 유형 | 내용 |
|---|---|
| 남은 한계 | 이 방식으로 못 막는 것, 조건부로만 성립하는 것 |
| 치른 대가 | 인덱스 추가로 느려진 쓰기, 늘어난 인프라 비용 |
| 미확인 구간 | 원인을 특정하지 못해 별도 과제로 분리한 영역 |
| 확장 적용 | 같은 패턴을 다른 곳에 적용한 이력 |
| 다음 단계 | 트래픽·규모가 늘면 필요한 전환 |
