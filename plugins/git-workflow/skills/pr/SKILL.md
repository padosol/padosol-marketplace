# pr

현재 작업 브랜치를 **PR(GitHub) / MR(GitLab) 으로 올리는** 스킬이다. 흐름은 항상 아래 순서를 지킨다:

0. 플랫폼 탐지 → 1. 시작 위치 파악·미커밋 변경 커밋 → 2. 브랜치·타겟·푸시 확인 → 3. 템플릿 결정 → 4. 이슈·제목·변경유형 → 5. 본문 작성(분량 예산) + estimate/spend 산출 → 6. 설명 조립 → 생성 → 7. 시간 기록·상세 근거 코멘트·결과 보고

> **핵심 제약 — 트레일러 금지**: 제목·본문 어디에도 `Co-Authored-By:`, `Signed-off-by:`, `🤖 Generated with …`, `Co-authored-by: Claude …` 등 **어떤 footer/trailer 도 넣지 않는다.** 호스트 CLI 의 `--signoff` 옵션도 **쓰지 않는다.** 이 스킬의 기본 동작이며, 하네스 기본값보다 우선한다.

> **출력 규칙 (중요)**: 사용자에게 보여줄 상태·결과 메시지는 **어시스턴트 채팅 텍스트로만** 출력한다 — `echo` 등으로 셸에서 실행하지 않는다. 설명(마크다운)은 **임시 파일에 먼저 써 두고** 호스트 CLI 에 파일로 넘긴다. 셸 명령줄 자체에는 `!`·백틱·미치환 `<...>` 플레이스홀더를 **절대** 넣지 않는다(파일 *내용*에 들어 있는 건 명령 치환으로 재해석되지 않으므로 안전하다). 이를 어기면 셸이 토큰을 명령 치환·리다이렉션으로 해석해 `syntax error near unexpected token` 으로 실패한다.

이하 본문에서 **`PR`** 은 host 에 따라 PR (GitHub) / MR (GitLab) 을 의미한다. 작업 브랜치는 보통 `.claude/worktrees/<name>` 아래 git worktree 로 체크아웃되어 있다.

## 0. 플랫폼 탐지 → 가이드 선택

먼저 어떤 git 플랫폼인지 **한 번** 결정한다 (결정 순서: `GF_HOST` 환경변수 > `.orch/settings.json` 의 `git_host` > `gh`/`glab` 인증 상태):

```bash
GF_HOST="${GF_HOST:-}"
if [ -z "$GF_HOST" ]; then
  d="$PWD"; orch=""
  while [ "$d" != "/" ]; do
    [ -f "$d/.orch/settings.json" ] && { orch="$d/.orch/settings.json"; break; }
    d="$(dirname "$d")"
  done
  if [ -n "$orch" ] && command -v jq >/dev/null 2>&1; then
    case "$(jq -r '.git_host // empty' "$orch" 2>/dev/null)" in
      github|gitlab) GF_HOST="$(jq -r '.git_host' "$orch")" ;;
    esac
  fi
fi
if [ -z "$GF_HOST" ]; then
  gh_ok=0; glab_ok=0
  command -v gh   >/dev/null 2>&1 && gh   auth status >/dev/null 2>&1 && gh_ok=1
  command -v glab >/dev/null 2>&1 && glab auth status >/dev/null 2>&1 && glab_ok=1
  if   [ "$gh_ok" = 1 ] && [ "$glab_ok" = 0 ]; then GF_HOST=github
  elif [ "$gh_ok" = 0 ] && [ "$glab_ok" = 1 ]; then GF_HOST=gitlab
  elif [ "$gh_ok" = 1 ] && [ "$glab_ok" = 1 ]; then
    echo "ERROR: gh / glab 양쪽 인증 — GF_HOST=github|gitlab 로 명시하거나 .orch/settings.json 의 git_host 설정" >&2; exit 2
  else
    echo "ERROR: gh / glab 모두 미인증 — 'gh auth login' 또는 'glab auth login' 후 재시도" >&2; exit 2
  fi
fi
case "$GF_HOST" in github|gitlab) ;; *) echo "ERROR: GF_HOST='$GF_HOST' 잘못된 값 (github|gitlab)" >&2; exit 2 ;; esac
echo "GF_HOST=$GF_HOST"
```

탐지가 비-0 으로 종료하면 (둘 다 인증 / 둘 다 미인증 / 잘못된 값) stderr 메시지 그대로 안내하고 중단한다.

결정된 플랫폼에 따라 **이후 모든 호스트 명령(템플릿 위치·라벨·생성·이슈 코멘트 등)은 이 스킬 디렉토리의 해당 가이드를 그대로 따른다**:
- `github` → `GITHUB_GUIDE.md`
- `gitlab` → `GITLAB_GUIDE.md`

먼저 해당 가이드를 Read 로 열어 둔다. 본문의 **`<가이드: 섹션명>`** 표기는 선택된 가이드의 동명 섹션 명령을 의미한다. **SKILL 본문에는 `if [ "$GF_HOST" = ... ]` 같은 플랫폼 분기를 두지 않는다 — 분기는 가이드 파일에만.**

## 1. 시작 위치 파악 · 미커밋 변경 커밋

현재 어느 repo / 브랜치에 있는지 확인한다.

```bash
git rev-parse --show-toplevel        # 현재 작업트리 루트 (= 어느 repo 인지)
git rev-parse --abbrev-ref HEAD      # 현재(소스) 브랜치
git status -s                        # 커밋 안 된 변경이 남아 있는지
git diff ; git diff --staged         # 남아 있다면 실제 변경 내용
```

- **커밋되지 않은 변경이 남아 있으면, 사용자에게 안내만 하고 멈추지 말고 먼저 분석해 커밋한 뒤 진행한다.** PR 에는 항상 커밋된 내용만 올라가므로, 이 단계에서 작업분을 누락 없이 커밋으로 만든다. 분석·커밋은 같은 플러그인의 `commit` 스킬 절차를 그대로 적용한다:
  - **① 파악** — `git diff`(+`git diff --staged`)로 *무엇이·왜* 바뀌었는지 읽는다(추측 금지). `git log --oneline -n 10` 으로 repo 의 메시지 컨벤션(언어·prefix)을 확인한다.
  - **② 범위** — 이미 staged 된 게 있으면 **그것만** 커밋한다(사용자가 의도적으로 골라둔 것). staged 가 없고 unstaged/untracked 만 있으면 변경 파일 목록을 한 번 보여주고 `git add -A`. 단, 빌드 산출물·로그·`node_modules`·비밀키처럼 **커밋하면 안 될 것**이 섞여 있으면 stage 하지 말고 알린다(`.gitignore` 확인). 서로 무관한 변경이 섞여 있으면 뭉치기 전에 **나눠 커밋할지 제안**한다.
  - **③ 커밋** — repo 컨벤션·언어에 맞는 메시지를 `git diff` 근거로 작성하고 `git commit -F -` heredoc 으로 커밋한다. **커밋 메시지에도 트레일러(`Co-Authored-By`·`Signed-off-by`·`Generated with` 등 어떤 footer 도)·`--signoff`·`--trailer` 를 넣지 않는다.**
  - **④ 확인** — `git log -1 --stat` 으로 트레일러 없는 커밋이 남았는지, `git status -s` 로 working tree 가 깨끗한지 확인한 뒤 다음 단계로 간다.
  - (커밋할 변경이 staged 도 unstaged 도 전혀 없으면 이 항목은 건너뛴다.)
- `develop`/`main` 같은 보호 브랜치에 그대로 서 있으면 PR 의 소스가 될 수 없다. 사용자에게 작업 브랜치를 확인한다.

## 2. 타겟 브랜치 · 원격 푸시 확인

**타겟 브랜치**(머지될 대상)를 정한다.

```bash
git ls-remote --heads origin develop   # develop 이 원격에 있으면 그게 기본 타겟
```

- `develop` 이 있으면 그것을, 없으면 repo 기본 브랜치(`main` 등)를 타겟으로 한다. 브랜치 prefix 가 `hotfix/` 면 기본 브랜치를 타겟으로 한다. 애매하면 **추측하지 말고** 사용자에게 묻는다.

**소스 브랜치를 원격에 푸시**한다(없으면 생성 명령이 실패한다).

```bash
git push -u origin HEAD               # 이미 추적 중이면 변경분만 올라감
```

## 3. PR 템플릿 결정 (리포 우선 → 내장 fallback)

`<가이드: PR 템플릿 위치>` 의 경로 우선순위대로 프로젝트 템플릿을 찾는다.

- **템플릿 파일이 있으면 그것을 쓴다.** 여러 개라 자동 선택이 애매하면 목록을 사용자에게 보여 주고 고르게 한다. 그 파일 내용을 읽어 베이스로 삼는다.
- **하나도 없으면** 스킬 내장 템플릿을 쓴다: `${CLAUDE_PLUGIN_ROOT}/skills/pr/template.md` 를 읽어 베이스로 삼는다. 내장 템플릿에는 호스트별로 다듬을 항목이 있으므로 `<가이드: 내장 템플릿 조정>` 을 함께 적용한다.

> 시간 추적(estimate·spend)은 **PR 이 아니라 연결된 이슈에 기록한다**(시간 단일 출처 = 이슈). 값 산출은 5단계, 이슈 기록은 7단계에서 하며, 호스트가 시간 추적을 지원할 때만 수행한다(`<가이드: 시간 추적>`).

> 호스트 CLI 의 `--template <이름>` 옵션은 **빈 템플릿 원문**을 그대로 채워 넣을 뿐이라 쓰지 않는다. 템플릿을 직접 읽어 **채운 마크다운**을 만들어 파일로 넘기는 방식을 쓴다(아래).

## 4. 연결 이슈 · 제목 · 변경 유형

- **연결 이슈**: 브랜치명 `type/<이슈번호>-설명`(예: `feat/42-download-history`)에서 이슈 번호를 뽑는다. 못 찾으면 사용자에게 묻고, 정말 없으면 **관련 이슈 섹션은 유지**하되 `Closes #...` 줄 대신 `없음` 으로만 적는다(부가 설명 없이). 크로스 리포면 `<네임스페이스>/<repo>#42` 형식(예: `padosol/lol-web#42`).
- **제목**: 변경 내용을 한 줄로 요약(repo 커밋 컨벤션·언어 따름). 초안이면 앞에 `Draft:` 를 붙이거나 6단계에서 `--draft` 를 쓴다.
- **변경 유형**: diff 와 브랜치 type 으로 판단해 **하나만** 고른다(택1). 본문에는 선택한 항목 **한 줄만 `[x]` 로 남기고 나머지 체크박스는 모두 삭제**한다. 두 유형 이상이 섞여 있으면 PR 분리를 제안한다.

## 5. 본문 작성(분량 예산) + estimate / spend 산출

이번 Claude Code 세션에서 한 작업을 근거로 템플릿의 **요약 / 변경 내용 / 테스트·검증** 섹션을 채운다(`git diff origin/<타겟>...HEAD` 로 실제 변경을 근거로, 추측 금지). **크로스 리포 영향**·**체크리스트**는 실제로 해당·수행한 항목만 `[x]` 로 채운다(시간 기록 항목은 7단계에서 기록할 예정이면 `[x]`).

### 5-1. 본문 분량 — 리뷰 진입점이지 작업 기록이 아니다

리뷰어는 **diff 를 옆에 띄워놓고** 본문을 읽는다. 그러니 **diff 를 읽으면 아는 것은 쓰지 않는다.** 본문에 남길 것은 diff 가 말해주지 않는 것뿐이다 — 왜 이 방식인지, 버린 대안, 어디부터 읽어야 하는지, 주의해서 볼 곳.

먼저 변경 규모를 재고(`git diff origin/<타겟>...HEAD --stat`), 그 규모의 예산 안에서 쓴다. 예산 단위는 **서술 줄** — 제목·빈 줄·체크박스를 뺀, 리뷰어가 실제로 읽는 문장 줄이다(정형 섹션이 20줄쯤 깔리므로 전체 줄 수로 재면 오작동한다):

| 규모 | 기준 | 서술 줄 상한 | 변경 내용 섹션 |
|---|---|---|---|
| 소 | ≤3 파일 | 6줄 | **섹션 통째로 생략** — 요약 1~2 문장 + 변경 유형 + 검증 1줄로 끝 |
| 중 | 4~9 파일 | 12줄 | 불릿 3~5 개, 각 1~2 줄 |
| 대 | ≥10 파일 또는 아키텍처·인터페이스 변경 | 20줄 | 불릿 최대 8 개, 각 1~2 줄 |

**금지** — 분량이 새는 전형적인 경로다:

- 파일 경로별 변경 나열 (`파일 X — …` 목록). Files changed 탭이 이미 보여준다
- diff 를 산문으로 옮긴 서술 (`A 를 B 로 갈아끼운다` 류). 코드가 이미 말한 것을 두 번 말하는 것
- 코드 블록 붙여넣기. 예외는 `## 머지 전에 필요한 것` 의 **손으로 실행할 명령**뿐
- 4 행 이상의 표, 작업 서사(`처음엔 ~했는데`), 자평(`꼼꼼히 확인했다`)
- 템플릿에 없는 섹션 임의 추가. 필요하면 기존 섹션 안에 넣는다 (템플릿의 `## 머지 전에 필요한 것` 은 수동 조치가 실제로 있을 때만 남기고, 없으면 삭제)

**넘치면 버리지 말고 옮긴다.** 설계 판단 근거·트러블슈팅 경위처럼 남길 가치는 있지만 리뷰에 필수는 아닌 내용은 본문에서 빼서 **7단계에서 PR 첫 코멘트로 게시**한다(`<details>` 로 접어서). 본문에는 `상세 근거는 아래 코멘트 참고` 한 줄만 남긴다.

**주제가 둘이면 PR 을 나눈다.** 변경 유형이 하나여도(둘이면 4단계에서 이미 분리 제안) 서로 무관한 주제 두 개가 한 PR 에 있으면 본문은 반드시 길어진다 — 본문을 늘려 해결하지 말고 분리를 제안한다. 사용자가 그대로 가겠다면 각 주제를 위 불릿 예산 안에서 쓴다.

### 5-2. estimate / spend 산출 (이 세션 기준)

**`<가이드: 시간 추적>` 이 "미지원" 이면 아래 산출을 통째로 건너뛰고 7단계의 시간 기록도 하지 않는다** (보고에는 그 사실을 명시). 지원하는 호스트에서는 estimate·spend 값을 산출해 둔다. 이 값은 본문이 아니라 **7단계에서 연결된 이슈에 기록**한다(시간 단일 출처 = 이슈):

```
/estimate <예상 시간>     # 이 작업의 예상 소요(계획값). 예: /estimate 2h
/spend <소비 시간>        # 이번 세션에서 PR 올리기까지 실제로 쓴 시간. 예: /spend 1h 30m
```

- 형식 단위: `mo w d h m`(예: `1d 4h`, `2h`, `1h 30m`). 기본 환산 `1w=5d`, `1d=8h`.
- 기록 형식·제약은 `<가이드: 시간 추적>` 을 따른다.
- **estimate — 변경 규모로 추론해 자동으로 넣는다. 작성자에게 묻지 않는다.** `git diff origin/<타겟>...HEAD --stat` 의 파일 수·증감 라인과 변경 성격(신규 로직 / 단순 수정 / 문서·설정)을 근거로 합리적인 계획값을 적는다(예: 문서·설정 소폭 `30m`, 함수 몇 개 `1h`~`2h`, 도메인 로직+테스트 `4h` 안팎).
- **spend — 이번 세션의 경과 시간을 확인해 자동으로 넣는다. 작성자에게 묻지 않는다.** 세션 트랜스크립트의 첫 이벤트 시각부터 현재까지를 구해 **5분 단위로 반올림**(스톱워치형 `1h 47m` 대신 사람 추정처럼 `1h 45m`), 최소 `5m` 으로 적는다:

  ```bash
  f=$(find ~/.claude/projects -name "$CLAUDE_CODE_SESSION_ID.jsonl" 2>/dev/null | head -1)
  start=$(jq -rs 'map(select(.timestamp != null))[0].timestamp // empty' "$f" 2>/dev/null)
  if [ -z "$start" ]; then echo UNKNOWN; else                           # 못 구하면 대화 흐름으로 추정
    el=$(( ( $(date -u +%s) - $(date -u -d "$start" +%s) ) / 60 ))        # 경과(분)
    el=$(( ( (el + 2) / 5 ) * 5 )); [ "$el" -lt 5 ] && el=5               # 5분 단위 반올림, 최소 5m
    h=$(( el / 60 )); m=$(( el % 60 ))
    if   [ "$h" -gt 0 ] && [ "$m" -gt 0 ]; then echo "${h}h ${m}m"        # → /spend 값
    elif [ "$h" -gt 0 ];                   then echo "${h}h"
    else                                        echo "${m}m"; fi
  fi
  ```
  - 결과가 `UNKNOWN` 이면(세션 ID·트랜스크립트·`jq` 부재) 대화 흐름으로 합리적으로 추정해 넣는다(그래도 묻지 않는다). 빈 `start` 로 `date` 가 엉뚱한 값(자정 기준 경과)을 내는 걸 막으려고 가드를 둔 것이다.
  - macOS 기본 `date` 는 `-d` 를 모른다. BSD 계열이면 `date -u -j -f '%Y-%m-%dT%H:%M:%S' "${start%.*}" +%s` 로 바꿔 계산한다.
  - spend 는 세션 시작~현재의 **벽시계 시간**이라 자리비움·세션 resume 이 끼면 부풀 수 있다. 변경 규모에 비해 비현실적으로 크면(예: 한 줄 수정에 `5h`) 상식선으로 낮춰 적는다.
  - 값은 호스트 시간추적에 그대로 기록된다. estimate·spend 모두 **자동으로 산출하되 6단계 요약에서 표시만** 하고, 작성자에게 확정·정정을 요구하지 않는다.

## 6. 설명 조립 → PR 생성

채운 마크다운(이슈·요약·변경유형·변경내용·테스트·크로스 리포 영향·체크리스트)을 **임시 파일**에 쓴다. 남은 플레이스홀더·빈 항목·HTML 주석은 지운다. **시간 기록 명령은 본문에 넣지 않는다**(연결 이슈에 기록 — 7단계).

```bash
DESC=$(mktemp)
# (편집 도구로 채운 최종 마크다운을 DESC 에 기록)
grep -vE '^[[:space:]]*$|^#|^[[:space:]]*- \[[ x]\]' "$DESC" | wc -l   # 서술 줄 수
```

**예산을 넘겼으면 제출하지 말고 줄인다.** 위 값이 해당 규모의 상한(소 6 / 중 12 / 대 20 서술 줄)을 넘으면 5-1 의 금지 목록부터 지우고(파일 나열·diff 재서술·코드 블록), 그래도 넘치면 판단 근거를 잘라내 7단계 코멘트로 보낸다. 줄인 뒤 다시 센다.

제출 직전, 사용자에게 **제목 / 타겟 / 연결 이슈 / draft 여부**를 한 번 요약해 보여주고 확인을 받는다. estimate·spend 는 5단계에서 자동 산출한 값(7단계에 이슈로 기록될 값)을 **표시만 하고 확인·정정을 요구하지 않는다**(작성자에게 묻지 않는다). 확인되면 `<가이드: PR/MR 생성>` 으로 생성한다 (입력: 소스 브랜치, 타겟 브랜치, 제목, 설명 파일).

- **담당자**: 작성자 본인을 항상 지정한다(`<가이드: PR/MR 생성>` 의 assignee 옵션).
- **유형 라벨**: `<가이드: 라벨 목록>` 으로 4단계 변경 유형(feat/fix/refactor/chore/ci/docs/test)에 해당하는 라벨이 프로젝트에 **이미 존재하면** 생성 시 라벨 옵션을 추가한다. 없으면 라벨 없이 생성한다 — 새 라벨을 만들지 않는다(라벨 체계는 프로젝트 관리 영역).
- 초안이면 `--draft` 를 추가한다. 소스 브랜치가 아직 원격에 없을 수 있으면 2단계 푸시를 먼저 했는지 확인한다.
- `--signoff`·`--fill`(자동 메시지)은 쓰지 않는다(트레일러·임의 본문 방지). 이슈 연결은 본문의 `Closes #` 로 한다.
- 명령에 `<...>` 토큰을 **그대로 넣지 말고** 실제 값으로 바꿔 넣는다. 설명은 항상 임시 파일로만 전달한다.

## 7. 시간 기록 → 상세 근거 코멘트 → 결과 보고

### 7-1. 연결 이슈에 시간 기록

PR 이 생성되면 5단계에서 산출한 estimate·spend 를 `<가이드: 연결 이슈에 시간 기록>` 으로 **연결된 이슈에 기록**한다(시간 단일 출처 = 이슈).

- `<가이드: 시간 추적>` 이 "미지원" 이면 이 단계를 건너뛰고 결과 보고에 그 사실을 명시한다.
- 크로스 리포 이슈면 가이드가 지정하는 repo 지정 옵션을 붙인다.
- 연결 이슈가 없으면(4단계에서 `Closes #` 삭제) 시간 기록을 건너뛰고 결과 보고에 그 사실을 명시한다.

### 7-2. 본문에서 덜어낸 상세 근거를 코멘트로

5-1 에서 본문 예산 밖으로 밀어낸 내용(설계 판단 근거·트러블슈팅 경위·검증 상세)이 있으면 `<가이드: PR 코멘트>` 로 **PR 첫 코멘트에 게시**한다. 밀어낸 내용이 없으면 이 단계를 건너뛴다 — 코멘트를 채우려고 본문에 없던 이야기를 새로 지어내지 않는다.

```markdown
<details>
<summary>설계 판단 근거</summary>

- (본문에서 덜어낸 판단·대안 비교·트러블슈팅 경위)

</details>
```

- 접은 블록 하나로 묶는다. 코멘트가 길어도 리뷰 화면을 밀어내지 않는다.
- 본문의 `상세 근거는 아래 코멘트 참고` 줄과 짝이 맞는지 확인한다(한쪽만 있으면 안 된다).

### 7-3. 결과 보고

사용자에게 요약을 남긴다. **첫 줄 + 불릿 3개** 고정 양식(제목 / 연결 이슈·시간 / PR 번호·URL). 번호는 생성 명령이 출력한 URL 의 마지막 숫자를 `<가이드: 번호 표기>` 형식으로 적는다:

```
MR !57 생성 완료: feat/42-download-history → develop
- 제목: 다운로드 이력 API 추가
- 연결 이슈: Closes #42 · estimate 2h · spend 1h 30m
- MR: !57 · https://gitlab.example.com/<group>/<repo>/-/merge_requests/57
```

- 연결 이슈가 없으면 `연결 이슈: 없음` 으로 적고, 시간을 기록하지 않았으면 그 사실이 드러나게 둔다(estimate·spend 는 이슈에 기록된 값).
- 호스트가 시간 추적을 지원하지 않으면 `시간 기록: 해당 없음 (호스트 미지원)` 으로 명시한다.

- 임시 파일(`$DESC` 등)은 정리한다.
- 사용자 확인으로 비워둔 항목(이슈 미연결·시간 미기록, draft 여부 등)이 있으면 그대로 명시한다.
