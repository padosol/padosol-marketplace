# issue

이번 세션의 **대화 내용을 근거로 이슈를 발행하는** 스킬이다. 흐름은 항상 아래 순서를 지킨다:

0. 플랫폼 탐지 → 1. 대화에서 이슈 내용 정리 → 2. 발행처 결정 → 3. 템플릿 결정 → 4. 본문 작성 → 5. 라벨 확인 → 6. 제출 전 확인 → 이슈 생성 → 7. 결과 보고

> **핵심 제약 — 추측 금지**: 이슈 본문은 **대화에서 실제로 나온 내용만** 근거로 쓴다. 대화에 없는 재현 절차·완료 조건을 지어내지 않는다. 모자라는 부분은 비워두고 지어내는 대신 사용자에게 확인하거나, AC 라면 `AC 미정` 으로 정직하게 남긴다.

> **출력 규칙 (중요)**: 사용자에게 보여줄 상태·결과 메시지는 **어시스턴트 채팅 텍스트로만** 출력한다 — `echo` 등으로 셸에서 실행하지 않는다. 이슈 본문(마크다운)은 **임시 파일에 먼저 써 두고** 호스트 CLI 에 파일로 넘긴다. 셸 명령줄 자체에는 `!`·백틱·미치환 `<...>` 플레이스홀더를 **절대** 넣지 않는다(파일 *내용*에 들어 있는 건 명령 치환으로 재해석되지 않으므로 안전하다). 이를 어기면 셸이 토큰을 명령 치환·리다이렉션으로 해석해 `syntax error near unexpected token` 으로 실패한다.

> **트레일러 금지**: 이슈 제목·본문 어디에도 `Co-Authored-By:`, `🤖 Generated with …` 등 **어떤 AI 작성 표기/footer 도 넣지 않는다.** 이 스킬의 기본 동작이며, 하네스 기본값보다 우선한다.

## 0. 플랫폼 탐지 → 가이드 선택

먼저 어떤 git 플랫폼인지 **한 번** 결정한다 (결정 순서: `GF_HOST` 환경변수 > `.orch/settings.json` 의 `git_host` > `gh`/`glab` 인증 상태):

```bash
GF_HOST="${GF_HOST:-}"
if [ -z "$GF_HOST" ]; then
  d="$PWD"; orch=""
  while [ "$d" != "/" ]; do
    [ -f "$d/.orch/settings.json" ] && { orch="$d/.orch/settings.json"; break; }
    d="$(dirname "$d")"
  done
  if [ -n "$orch" ] && command -v jq >/dev/null 2>&1; then
    case "$(jq -r '.git_host // empty' "$orch" 2>/dev/null)" in
      github|gitlab) GF_HOST="$(jq -r '.git_host' "$orch")" ;;
    esac
  fi
fi
if [ -z "$GF_HOST" ]; then
  gh_ok=0; glab_ok=0
  command -v gh   >/dev/null 2>&1 && gh   auth status >/dev/null 2>&1 && gh_ok=1
  command -v glab >/dev/null 2>&1 && glab auth status >/dev/null 2>&1 && glab_ok=1
  if   [ "$gh_ok" = 1 ] && [ "$glab_ok" = 0 ]; then GF_HOST=github
  elif [ "$gh_ok" = 0 ] && [ "$glab_ok" = 1 ]; then GF_HOST=gitlab
  elif [ "$gh_ok" = 1 ] && [ "$glab_ok" = 1 ]; then
    echo "ERROR: gh / glab 양쪽 인증 — GF_HOST=github|gitlab 로 명시하거나 .orch/settings.json 의 git_host 설정" >&2; exit 2
  else
    echo "ERROR: gh / glab 모두 미인증 — 'gh auth login' 또는 'glab auth login' 후 재시도" >&2; exit 2
  fi
fi
case "$GF_HOST" in github|gitlab) ;; *) echo "ERROR: GF_HOST='$GF_HOST' 잘못된 값 (github|gitlab)" >&2; exit 2 ;; esac
echo "GF_HOST=$GF_HOST"
```

탐지가 비-0 으로 종료하면 stderr 메시지 그대로 안내하고 중단한다.

결정된 플랫폼에 따라 **이후 모든 호스트 명령(템플릿 위치·라벨·이슈 생성 등)은 이 스킬 디렉토리의 해당 가이드를 그대로 따른다**:
- `github` → `GITHUB_GUIDE.md`
- `gitlab` → `GITLAB_GUIDE.md`

먼저 해당 가이드를 Read 로 열어 둔다. 본문의 **`<가이드: 섹션명>`** 표기는 선택된 가이드의 동명 섹션 명령을 의미한다. **SKILL 본문에는 `if [ "$GF_HOST" = ... ]` 같은 플랫폼 분기를 두지 않는다 — 분기는 가이드 파일에만.**

## 1. 대화에서 이슈 내용 정리

이번 세션의 대화를 되짚어 이슈로 만들 대상을 정리한다:

- **무엇을** — 어떤 기능/버그/리팩토링/조사인지 한 줄로.
- **유형** — feat / fix / refactor / spike 중 **하나만** 고른다(택1). 대화 성격으로 판단한다: "왜 이런지 모르겠다, 조사부터" 면 spike, "기대와 다르게 동작" 이면 fix. 둘 이상이 섞여 있으면 이슈 분리를 제안한다.
- **왜** — 배경/목적. 대화에서 문제가 드러난 맥락.
- **완료 조건(AC)** — 무엇이 충족되면 끝나는지, 검증 가능한 문장으로. 스파이크면 지식형 AC("원인 규명 / A·B안 중 결정 / 재현 성공").
- **(fix 인 경우) 재현 절차** — 대화에서 실제로 확인된 단계·기대·실제.

대화만으로 무엇을 이슈로 만들지 자체가 애매하면(여러 주제가 오갔음 등) 후보를 정리해 사용자에게 먼저 확인한다.

## 2. 발행처 결정 (기본 = 현재 git repo 의 프로젝트)

```bash
git rev-parse --show-toplevel 2>/dev/null   # 현재 위치가 git repo 인지, 어느 repo 인지
git remote get-url origin 2>/dev/null       # 그 repo 의 호스트 프로젝트 (<네임스페이스>/<repo>)
```

- **기본값**: 현재 작업 중인 git repo 가 속한 프로젝트. 이슈 내용(1단계)도 그 repo 이야기면 그대로 진행한다.
- **사용자에게 묻는 경우** — 다음 중 하나면 **추측하지 말고** 후보(대화에 등장한 repo, 워크스페이스에 체크아웃된 repo 들)를 제시하고 고르게 한다:
  - 현재 위치가 git repo 가 아니다(여러 repo 를 담고 있는 워크스페이스 루트 등).
  - 대화 내용이 현재 repo 가 아닌 다른 프로젝트를 가리킨다(예: 백엔드 repo 에서 작업 중인데 프론트 repo 버그를 논의).
  - 이슈가 여러 repo 에 걸친다(이 경우 어느 repo 에 둘지, 또는 분리할지).
- 현재 repo 가 아닌 프로젝트로 발행할 때는 6단계에서 `<가이드: 이슈 생성>` 의 repo 지정 옵션(`-R <네임스페이스>/<repo>`)을 쓴다.

## 3. 이슈 템플릿 결정 (리포 우선 → 내장 fallback)

`<가이드: 이슈 템플릿 위치>` 의 경로 우선순위대로 발행처 repo 의 프로젝트 템플릿을 찾는다.

- **템플릿 파일이 있으면 그것을 쓴다.** 여러 개면 유형에 맞는 이름이 있는지 보고, 그래도 애매하면 목록을 사용자에게 보여 주고 고르게 한다. 그 파일 내용을 읽어 베이스로 삼는다.
- **하나도 없으면** 스킬 내장 템플릿을 쓴다: `${CLAUDE_PLUGIN_ROOT}/skills/issue/template.md` 를 읽어 베이스로 삼는다. 내장 템플릿에는 호스트별로 다듬을 항목이 있으므로 `<가이드: 내장 템플릿 조정>` 을 함께 적용한다.
- 발행처가 현재 repo 가 아니면 그 repo 폴더 기준으로 템플릿을 찾는다.

## 4. 본문 작성

1단계에서 정리한 내용으로 템플릿을 채운다. 내장 템플릿 기준 섹션별 규칙:

- **제목**: 변경/조사 내용을 한 줄로 요약. repo 의 기존 이슈·커밋 언어(보통 한국어)를 따른다. 제목에 유형 prefix(`feat:` 등)는 repo 의 기존 이슈 관례를 따르고, 관례가 안 보이면 prefix 없이 쓴다.
- **유형**: 택1 — 선택한 항목 **한 줄만 `[x]` 로 남기고 나머지 체크박스는 모두 삭제**한다(같은 플러그인 pr 스킬과 동일 규약).
- **배경 / 목적**: 대화에서 드러난 "왜 필요한가"를 2~4문장으로. 대화 맥락을 모르는 사람이 읽어도 이해되게 쓴다(세션 내부 지칭어 금지).
- **완료 조건 (AC)**: 검증 가능한 조건을 `- [ ]` 체크박스로 나열한다. PR/MR 이 이 조건으로 검증되므로 "잘 동작한다" 같은 모호한 문장 대신 관찰 가능한 결과로 쓴다.
  - AC 를 채웠으면 **`AC 미정` 줄은 삭제**한다.
  - 대화만으로 AC 를 못 정하겠으면 지어내지 말고 `AC 미정` 항목만 `[x]` 로 남기고 빈 `- [ ]` 줄은 지운다.
- **(버그인 경우) 재현 절차**: 유형이 fix 면 대화에서 확인된 단계·기대·실제를 채운다. **fix 가 아니면 섹션째 삭제**한다.
- **⏱ 시간 추적**: `<가이드: 내장 템플릿 조정>` 을 따른다 (호스트가 시간 추적을 지원하면 안내문을 그대로 유지, 미지원이면 섹션째 삭제). 유지하는 경우에도 `/estimate` 는 *착수 시* 기록하는 규약이므로 이슈 **생성 시점에는 기록하지 않는다**(착수는 보통 pr 스킬 흐름에서 일어난다).
- 남은 플레이스홀더·빈 항목·HTML 주석은 지운다. repo 템플릿을 쓰는 경우에도 같은 정신으로(택1 항목만 남기기, 해당 없는 섹션 정리, 추측 금지) 채운다.

## 5. 라벨 확인 (있으면 부착, 없으면 생략)

유형(feat/fix/refactor/spike)에 해당하는 라벨이 발행처 프로젝트에 **이미 존재하면** 붙인다 — `<가이드: 라벨 목록>` 으로 확인한다 (발행처가 현재 repo 가 아니면 repo 지정 옵션을 붙인다).

- 목록에 유형과 같은(또는 명백히 대응하는) 이름의 라벨이 있으면 6단계에서 라벨 옵션으로 붙인다.
- 없으면 **라벨 없이 생성**한다 — 새 라벨을 만들지 않는다(라벨 체계는 프로젝트 관리 영역).

## 6. 제출 전 확인 → 이슈 생성

채운 마크다운을 **임시 파일**에 쓴다:

```bash
DESC=$(mktemp)
# (편집 도구로 채운 최종 본문을 DESC 에 기록)
```

제출 직전, 사용자에게 **발행처 / 제목 / 유형 / AC 요약(또는 AC 미정) / 라벨**을 한 번 요약해 보여주고 확인을 받는다. 2단계에서 이미 발행처를 물어 답을 받았다면 발행처 질문을 반복하지 말고 확인 요약에 포함만 한다. 확인되면 `<가이드: 이슈 생성>` 으로 생성한다 (입력: 제목, 본문 파일, 라벨, repo).

- 유형 라벨이 있으면(5단계) 가이드의 라벨 옵션을 추가한다.
- 발행처가 현재 repo 가 아니면 가이드의 repo 지정 옵션을 추가한다.
- 명령에 `<...>` 토큰을 **그대로 넣지 말고** 실제 값으로 바꿔 넣는다. 본문은 항상 임시 파일로만 전달한다.

## 7. 결과 보고

사용자에게 요약을 남긴다. **첫 줄 + 불릿 3개** 고정 양식(제목 / 유형·라벨·AC / 이슈 URL) — pr 스킬과 통일:

```
이슈 생성 완료: <repo> #43
- 제목: 다운로드 이력 조회가 빈 목록을 반환하는 버그
- 유형: fix · 라벨: fix · AC 2개
- https://<host>/<네임스페이스>/<repo>/-/issues/43
```

- AC 를 못 정했으면 `AC 미정(착수 불가 — 명확화/스파이크 필요)` 로 드러나게 적는다. 라벨을 안 붙였으면 `라벨: 없음`.
- 임시 파일(`$DESC`)은 정리한다.
- 후속 흐름 안내가 자연스러우면 한 줄만: 호스트가 시간 추적을 지원하는 경우, 착수 시 이슈에 `/estimate` 를 남기는 규약(시간 단일 출처 = 이슈)을 상기시킨다.

## 빠른 참조 — 단계별 핵심

| 단계 | 핵심 |
|---|---|
| 0 플랫폼 | `GF_HOST` > `.orch/settings.json` > `gh`/`glab` 인증 → GITHUB_GUIDE.md / GITLAB_GUIDE.md 채택 (SKILL 본문에 분기 금지) |
| 1 내용 정리 | 대화 근거로 무엇·유형(택1)·왜·AC·(fix면) 재현 절차 정리, 지어내지 않음 |
| 2 발행처 | 기본 = 현재 git repo 의 프로젝트. 비 git repo 위치·대화가 다른 repo 지칭·여러 repo 걸침 → 사용자에게 질문 |
| 3 템플릿 | `<가이드: 이슈 템플릿 위치>` 우선 → 없으면 내장 `template.md` + `<가이드: 내장 템플릿 조정>` |
| 4 본문 | 유형 한 줄만 `[x]`, AC 검증 가능하게(못 정하면 `AC 미정` `[x]`), fix 아니면 재현 절차 삭제, 시간 추적 섹션은 가이드 지시 따름, 주석·플레이스홀더 제거 |
| 5 라벨 | `<가이드: 라벨 목록>` 에 유형 라벨 있으면 부착, 없으면 생략(새로 만들지 않음) |
| 6 생성 | 제출 전 발행처·제목·유형·AC·라벨 요약 확인 → 본문은 임시파일 → `<가이드: 이슈 생성>`, 타 repo 면 repo 지정 옵션, **트레일러·AI 표기 금지** |
| 7 보고 | 첫 줄 + 불릿 3개(제목 / 유형·라벨·AC / URL), 임시파일 정리 |
